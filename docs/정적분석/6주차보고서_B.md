# 6주차 과제_B — 정적 분석 출력 정리

**사람**: 왕은서 (본인)
**기간**: 2026-08-02 (6주차 Day 1~3 분량)
**브랜치**: `feature/static-adapter` (`origin/main`에서 분기)

6주차부터 역할 번호와 A~D 문자를 통일했다.

| 역할 | 문자 | 담당 | 6주차 업무 |
|---|---|---|---|
| 역할 1 | A | 유예원 | 오케스트레이터 리드 (`main.py`, 통합 스펙) |
| 역할 2 | B | 왕은서 (본인) | **정적 분석 출력 정리 (어댑터 + 단위 테스트)** |
| 역할 3 | C | 김은아 | 동적 분석 출력 정리 |
| 역할 4 | D | 백소정 | 네트워크 마무리 + 종합 위험도 점수 |

> 주의: `src/static_analyzer/` 각 파일 상단 주석의 "(A 작성)", "(C 작성)", "(원래 D 담당)"
> 표기는 **3주차 당시의 역할 문자**라 위 표와 다르다. 5주차 네트워크 모듈의 A~D도 또 다른
> 배정이었다. 코드 주석의 문자는 이력 표시로만 읽어야 한다.

## 1. 시작 상황 — 다른 역할이 아직 시작 전이었다

6주차 계획서상 B의 Day 1 과제는 **"역할 1(A)의 스펙에 맞추기 위한 필드 매핑 정리"**였다.
그런데 작업을 시작한 시점에 **A의 통합 스펙이 아직 나오지 않았고, 다른 팀원들도 6주차
과제를 시작하지 않은 상태**였다. 문자 그대로 읽으면 B는 아무것도 할 수 없다.

그래서 먼저 "정말로 A를 기다려야 하는가"를 확인했고, **기다릴 필요가 없다는 결론**을 냈다.

**근거**: 팀 합의 스펙은 이미 1주차에 만들어져 있다 — `schemas/static_report.schema.json`.
`schemas/README.md`에도 이렇게 못 박혀 있다.

> 각 모듈 구현 시(2주차~5주차) 이 스키마의 필드명을 그대로 사용해서 결과 JSON을 생성한다.
> (…) 임의로 필드명을 바꾸면 6주차 통합(`main.py` 오케스트레이터)에서 파싱 에러가 난다.

A가 6주차에 쓸 통합 스펙은 이 1주차 스키마를 뒤엎기보다 그 위에서 나올 가능성이 크다.
따라서 **어댑터의 목표 포맷을 `static_report.schema.json`으로 잡고 먼저 진행하고**, A가
다른 걸 확정하면 어댑터의 출력부 한 곳만 고치면 된다.

이 판단은 5주차 네트워크 모듈에서도 같은 방식이 통했던 경험을 따른 것이다. 당시에도
A/B/C의 캡처·파서 결과가 없는 상태에서 D 역할(화이트리스트·판별)을 먼저 진행했다.

## 2. Day 1 — 필드 매핑 조사

조사해 보니 **현재 구현 출력과 1주차 팀 스키마가 실제로 맞지 않았다.** 이름만 다른
수준이 아니라 **데이터가 아예 생성되지 않는 항목**이 있었다.

### 양쪽 형태

| | 최상위 필드 |
|---|---|
| 현재 구현 (`schema.py`의 `StaticAnalysisResult`) | `meta`, `manifest`, `certificate`, `code_analysis`, `strings`, `third_party_sdks`, `risk_score`, `errors` (8개) |
| 팀 스키마 (`static_report.schema.json`) | `meta`, `permissions`, `components`, `risk_score` (4개, 전부 required) |

### 주요 불일치

| 스키마가 요구 | 조사 당시 상태 |
|---|---|
| `meta.apk_name`, `meta.analyzed_at` (required) | **아예 생성 안 함** |
| `permissions[].risk_level`, `abuse_example` | **아예 생성 안 함** (문자열 배열뿐) |
| `components[].type`, `exported` | 4개 리스트로 분리 + 이름만 flatten |
| `components[].intent_filters` | **파싱 단계에서 버려짐** |
| `risk_score` | float 0.0~1.0 (스키마는 객체) |
| `risk_score.breakdown` | **생성 안 함** |

특히 심각했던 두 가지:

**(1) `intent_filters`가 파싱 단계에서 사라진다.** `manifest_parser.py`가
`elem.find("intent-filter") is not None`으로 **존재 여부만 bool로 쓰고 내용을 버리고
있었다.** 원본 `AndroidManifest.xml`에는 다 들어있는데 파서가 읽지 않는 것이라,
어댑터로는 절대 복원할 수 없고 원천 코드를 고쳐야만 했다.

이 필드는 실질적으로 중요하다. `BOOT_COMPLETED`(부팅 시 자동 실행),
`SMS_RECEIVED`(문자 수신 가로채기) 같은 값이 여기 들어있고, 우리가 3~6월에 분석했던
Anubis의 핵심 동작이 정확히 이 지점이다.

**(2) `analyze_static()`의 반환값만으로는 어떤 파일을 분석했는지 알 수 없다.**
`extract_apk()`가 내부적으로 `apk_path`를 반환하는데 `analyzer.py`가 `meta`만 꺼내 쓰고
버린다. 스키마의 required 필드인데 만들 방법이 없었다.

### 산출물

`docs/정적분석/6주차_B_필드매핑.md` — 필드별 매핑, 근거 라인 번호, A/C/D에게 넘길 질의
목록까지 정리했다.

## 3. Day 2 — `manifest_parser.py` 보강

어댑터로 못 채우는 것부터 원천에서 해결했다.

- `_get_intent_filters()` 신설 — intent-filter 안의 `action`/`category` 이름을 순서 유지
  중복 제거로 수집. `<data>`(딥링크 scheme/host)는 스키마에 자리가 없어 제외
- `_get_component_info()` 반환에 `intent_filters` 추가
- `parse_manifest()`에 `type`이 붙은 `components` 리스트 추가

**기존 7개 필드는 그대로 뒀다.** `risk_scorer.calculate_risk()`가
`dangerous_permissions`/`exported_components`를 참조 중인데 그쪽은 D 영역이라
건드리면 안 되기 때문이다.

### 놓치기 쉬웠던 경계 하나

빈 `<intent-filter/>`가 있으면 **`exported`는 `True`인데 `intent_filters`는 빈 배열**이다.
`exported` 추론은 "intent-filter 태그가 있는가"로, `intent_filters`는 "그 안에
action/category가 있는가"로 결정되기 때문이다. 둘을 같은 조건으로 묶으면 `exported`
추론이 틀어진다. 주석과 테스트로 고정해 뒀다.

### 검증

합성 XML 7개 케이스를 통과시킨 뒤, **실제 APK(`로컬 테스트 APK`)로도 확인**했다.
`parse_manifest()`는 androguard만 쓰고 jadx/apktool이 필요 없어서 지금 환경에서도 돌아간다.

```
[activity] com.example.sampleapp.ipc.ExportedActivity  exported=True
    - android.intent.action.VIEW
    - android.intent.category.DEFAULT
    - android.intent.category.BROWSABLE
```

외부 앱이나 브라우저 링크로 열 수 있는 exported 액티비티인데, 수정 전에는 이름 하나만
남고 이 정보가 전부 사라졌다. 이 작업이 왜 필요했는지 실물로 확인된 셈이다.

## 4. Day 2~3 — `static_adapter.py` 작성

`to_static_report(result, apk_path=None, include_extra=True)` — 8개 필드를
`static_report.json` 형태로 변환한다. **분석 로직은 전혀 없고 순수 dict 변환만 한다.**
그래서 실제 APK나 jadx/apktool 없이 테스트할 수 있고, 실패하거나 느려질 일이 없다.

### 어댑터가 못 채워서 원천에 추가한 것

- `apk_extractor` → `meta.apk_name`
- `analyzer` → `meta.analyzed_at` (변환 시점이 아니라 **분석 시점**이어야 의미가 있어
  `analyze_static()` 진입 시 기록. 네트워크 모듈의 `capture_started_at`과 같은 방식)

### `ABUSE_EXAMPLES` 신설

권한 16개의 악용 예시를 `manifest_parser`에 추가했다. 팀이 분석한 Anubis 동작을 근거로
썼다 (접근성 서비스 악용, 오버레이 피싱, OTP 문자 탈취, 드로퍼, 부팅 시 지속성 등).

여기서 **역할 경계를 명확히 나눈 것이 핵심**이다:

| | `PERMISSION_WEIGHTS` | `ABUSE_EXAMPLES` |
|---|---|---|
| 쓰임 | 위험도 점수 **계산에 직접 들어감** | 사용자에게 보여줄 **설명 텍스트** |
| 항목 추가 시 | D의 점수가 바뀜 → **단독 수정 불가** | 점수 영향 없음 → **자유롭게 추가 가능** |
| 담당 | D | B |

즉 **"설명은 B가 지금 채우고, 등급은 D와 함께 정한다"**로 분리했다. 덕분에 D를 기다리지
않고도 사용자에게 보여줄 내용을 만들 수 있었다.

### 설계 판단 세 가지

**(1) `breakdown`은 일부러 만들지 않았다.** 어댑터가 접근할 수 있는 건 권한 가중치뿐인데,
실제 raw 점수에는 `exported_components × 2`, `suspicious_api_calls × 3`, 난독화 +15,
리플렉션 +10, 동적 로딩 +15, `suspicious_strings × 2`가 함께 들어간다. **권한만 재현하면
breakdown 합계가 total과 맞지 않는다.** "근거"의 합이 총점과 다르면 오히려 혼란스러우므로
D에게 요청 사항으로 넘겼다.

**(2) `errors`에 어댑터 경고를 이어 붙인다.** `risk_score` 계산이 실패하면 스키마상
`total`이 required + number라 `null`을 못 넣어 `0.0`을 넣어야 하는데, 그대로 두면
**"위험도 0 = 안전한 앱"으로 읽힌다.** 그래서 어댑터가 값을 임의로 채운 자리마다 경고를
남기도록 했다. 원본 리스트는 복사해서 쓰므로 입력 dict를 변조하지 않는다.

**(3) `manifest`가 `None`일 때 예외 대신 빈 배열로 계속 진행한다.** 정적 분석 모듈 전체가
"부분 실패해도 계속" 정책이라 어댑터만 뒤집으면 일관성이 깨진다. A의 스펙 확정 시 바꿀
지점이라고 주석에 표시해 뒀다.

## 6. 구현 중 잡은 버그 두 개

두 개 다 **`jsonschema` 검증을 붙이지 않았으면 통합 단계까지 갔을 문제**다.

**(1) `min_sdk` / `target_sdk`가 없을 때 `None`을 내보내 스키마 검증에 걸렸다.**
두 필드는 optional이지만 **넣을 거면 `integer`여야 하고 `null`은 허용되지 않는다.**
`optional`을 "없으면 `null`을 넣어도 된다"로 착각한 것이었다. 값이 정수일 때만 키를
포함하도록 고쳤다.

**(2) `risk_score`가 `bool`일 때 최고 위험 점수로 둔갑했다.**
파이썬에서 `True`는 `int`의 하위 타입이라 `isinstance(True, int)`가 참이다. 방어하지 않으면
`risk_score = True`가 `total = 100.0`이 된다. `isinstance(raw, bool)` 검사를 추가했다.

### 다른 역할에게 넘긴 항목

**A(유예원)에게 4건** — 그중 최우선은 **`errors`를 통합 스펙에 반드시 넣는 것**이다.
`analyze_static()`은 부분 실패 시 예외를 던지지 않으므로 `try/except`로는 실패를 감지할
수 없고, `errors`가 비어 있는지 보는 것이 유일한 방법이다.

**D(백소정)에게 4건** — 그중 중요한 것은 **`PERMISSION_WEIGHTS`에 권한이 5개뿐**이라
`CAMERA`, `RECORD_AUDIO`, `READ_CONTACTS` 등이 전부 `low`로 떨어지는 문제다.
이 표는 `calculate_risk()`가 그대로 합산에 쓰므로 B가 임의로 늘리면 D의 점수가 바뀐다.
또 하나는 `strings.urls`(코드에 하드코딩된 주소)를 네트워크 모듈의 `suspicious.domains`
(실제 통신한 주소)와 **대조하자는 제안**이다. 단일 모듈로는 못 내는 근거라 발표 자료에서도
정적·네트워크를 잇는 볼거리가 될 것 같다.

**C(김은아)에게 1건** — 동적 모듈도 어댑터를 짜기 전에 `dynamic_analyzer/schema.py`와
`schemas/dynamic_report.schema.json`을 먼저 대조해 보길 권했다. 정적 쪽은 8개 필드 중
4개가 스키마에 자리가 없었고, 파싱 단계에서 아예 버려진 데이터도 있었다. 어댑터를 다 짜고
나서 발견하면 원천 코드를 다시 고쳐야 한다.

## 8. 환경 관련 기록

- **`jadx`, `apktool`이 설치돼 있지 않아 `analyze_static()` 전체 실행은 불가능하다**
  (`extract_apk`가 디컴파일 단계에서 실패). 그래서 단위 테스트는 fixture dict 기반으로
  작성했다. 어댑터는 순수 dict 변환이라 이 방식으로 충분히 검증된다.
- `parse_manifest()`는 androguard만 쓰므로 실제 APK로 검증 가능했다.
- **저장소 안에는 APK가 없고**, CLAUDE.md에 언급된 `anubis.apk` / `syssecapp.apk`도 이
  PC에서 찾지 못했다. 검증에 쓴 `로컬 테스트 APK`는 `Downloads` 폴더에 있던 것이다.
- `androguard`가 loguru로 DEBUG 로그를 대량 출력한다. 파이프라인 통합 시 다른 로그가
  묻히므로 A에게 로그 레벨 조정을 건의했다.

## 9. Day 4 — A/C/D 결과 합류 (2026-08-03)

A, C, D의 6주차 산출물이 한꺼번에 들어와서 상황이 크게 바뀌었다.

### 9-1. A가 어댑터를 안 쓰기로 했다

A의 `main.py`(`feature/orchestrator`) 주석에 명시돼 있다.

> B가 만든 `to_static_report()`는 여기서 **의도적으로 쓰지 않는다**. 8필드 원본을
> 변환 없이 그대로 통과시키는 정책

**A의 판단이 맞다.** 2절에서 정리한 불일치들이 "변환하지 않으면" 대부분 사라진다.
스키마에 자리가 없던 `certificate`/`code_analysis`/`strings`/`third_party_sdks` 4개가
그대로 살고, `risk_score` 실패 시 `total=0.0`으로 강제되는 문제(4절에서 경고로
우회했던 것)도 애초에 생기지 않는다 — `None` + `module_status="partial"`로 드러난다.

A는 "Day 1 스펙을 문서로만 만들어두고 실제로 공유하지 않아 B가 못 봤다"고 밝혔다.

**그래서 1절의 판단이 틀렸던 것인가?** 그렇지는 않다고 본다. 어댑터의 목표 포맷을
1주차 스키마로 잡은 것은 결과적으로 빗나갔지만, 그 조사 과정에서 나온 것들은
포맷과 무관하게 살아남았다:

| 산출물 | Day 4 시점 상태 |
|---|---|
| `intent_filters` 수집 (파싱 단계에서 버려지던 것) | **8필드 안에 그대로 포함 — 통합에서 이득** |
| `meta.apk_name` / `analyzed_at` | 8필드 안에 포함 |
| `ABUSE_EXAMPLES` 16개 | 파이프라인 미사용, 대시보드(7~8주차)용으로 남음 |
| `manifest_parser` 회귀 테스트 16개 | 원천 코드 테스트라 그대로 유효 |
| `static_adapter.py` + 어댑터 테스트 | 파이프라인에서 빠짐 |

버려진 것은 어댑터 본체뿐이고, **원천 코드를 고쳐야만 했던 것들은 전부 남았다.**
Day 1에 "어댑터로는 절대 복원할 수 없다"고 판단해 원천부터 고친 것이 결과적으로
맞는 선택이었다.

### 9-2. D가 질의 4건을 전부 반영했다

`fix/static-permission-weights` 브랜치:

- `PERMISSION_WEIGHTS` 5개 → 20개 확장 (`CAMERA`/`RECORD_AUDIO`/`READ_CONTACTS` 포함)
- **표만 늘려서 끝나지 않았다** — `calculate_risk()`가 `dangerous_permissions`(8점 이상만
  걸러진 목록)만 합산해서 **8점 미만 권한은 표에 있어도 점수에 안 잡히던 버그**를 같이 고침
- `calculate_risk_with_breakdown()` 신설 — 4절에서 "권한만 재현하면 합계가 안 맞는다"며
  만들지 않았던 `breakdown`을 D가 원천에서 해결해 줬다
- `certificate.is_self_signed` 가중치 10 신설

### 9-3. 병합 — 예고된 충돌 1건

D가 미리 알려준 대로 `manifest_parser.py`에서 충돌이 났다. `ABUSE_EXAMPLES`(B)와
`DANGEROUS_PERMISSION_THRESHOLD`(D)가 `PERMISSION_WEIGHTS` 바로 뒤 같은 위치에
추가돼서다. **내용이 안 겹쳐 둘 다 살렸고**, 병합 후 기존 44개 테스트가 전부 통과했다.

### 9-4. 아무도 안 챙기고 있던 구멍 — breakdown 호출부

D는 `calculate_risk_with_breakdown()`을 **"어댑터에서 이 함수로 갈아타면 됨"**이라고
B의 어댑터용으로 만들었다. 그런데 A가 어댑터를 안 쓰기로 했다. 결과적으로:

- `analyzer.py`는 여전히 `calculate_risk()`(float만 반환)만 호출
- A의 `main.py` 최상위 `risk_score.breakdown`도 `None`
- **D가 만든 breakdown을 부르는 코드가 아무 데도 없었다**

각자 자기 영역에서는 맞게 했는데 사이가 비어 있는 전형적인 경우다. 그래서
**`analyzer.py`가 직접 부르도록 배선했다.** 어댑터를 거치지 않는 8필드 원본 경로에서도
근거가 나온다.

설계에서 신경 쓴 것은 **`risk_score`의 타입을 안 바꾼 것**이다. `schema.py`가
`risk_score: float`을 팀 계약으로 못 박고 있고 A의 `main.py`가 그걸 그대로 통과시키므로,
객체로 바꾸면 그쪽이 깨진다. D도 같은 이유로 `calculate_risk()`의 반환형을 유지했다.
그래서 근거는 `risk_breakdown` **형제 필드**로 뺐다. 계산이 실패하면 둘 다 `None`이라
"점수는 있는데 근거만 없는" 어긋난 상태가 안 생긴다.

### 9-5. 테스트 44개 → 67개

`tests/test_analyzer.py`를 새로 만든 이유가 있다. **기존 어댑터 테스트는 전부 fixture
dict 기반이라 `analyze_static()`이 정말 그 모양을 만드는지는 검증하지 못한다.**
Day 1에 `intent_filters`가 파싱 단계에서 버려지던 걸 뒤늦게 발견한 것과 같은 유형의
구멍이다. 하위 단계 6개를 monkeypatch해서 jadx/apktool 없이 조립 로직만 검증한다.

Day 3과 마찬가지로 **코드를 일부러 되돌려 테스트가 실제로 잡는지 확인했고, 4건 전부
잡혔다.** 그중 하나(`analyzer`가 `risk_breakdown`을 안 채우게 함)는 어댑터 테스트
59개가 **전부 통과해 버렸고** `test_analyzer.py`만 5개 실패했다 — 새 테스트 파일이
왜 필요했는지가 그대로 드러난 셈이다.

### 9-6. 실제 APK 재검증 — 절반만 됐다

D가 "`로컬 테스트 APK`로 다시 돌려봐 달라"고 요청한 것에 대한 결과다.

| 항목 | 결과 |
|---|---|
| `is_self_signed` 가산점이 점수에 실제 영향 | **확인** — total `0.060` → `0.160` (+0.10) |
| breakdown 합계 == raw | **확인** — 16 == 16 |
| 어댑터 출력이 팀 스키마 검증 통과 | **확인** |
| `intent_filters`가 실 APK에서 살아있는지 | **확인** (exported 3개 전부 값 있음) |
| `CAMERA` 등이 medium/high로 잡히는지 | **검증 불가** |

`로컬 테스트 APK`의 권한이 `INTERNET`과 자체 정의 권한 **2개뿐**이라 확장된 권한 표를 실제
APK로 확인할 방법이 없다. 이 PC 전체를 검색해도 다른 APK는 에뮬레이터 스킨 오버레이뿐이다.
합성 데이터로는 정상 동작을 확인했지만, **권한이 많은 실제 샘플이 없으면 진짜 검증이
안 된다.** D가 지적한 `NORMALIZATION_CAP` 재조정도 같은 샘플이 있어야 가능하다.
7주차의 실질적인 선결 과제다.

### 9-7. A의 골격 연결 확인

`feature/orchestrator`의 `main.py`를 받아 정적 stage가 물리는지 확인했다.
**B 쪽은 수정 없이 그대로 꽂힌다** — `ok`/`partial` 판정, `package_name` 추출,
`risk_breakdown` 통과 전부 정상이다.

확인 중 A에게 넘길 것 2건이 나왔다:

1. **`main.py`가 `frida` 없이는 import조차 안 된다.** `frida_controller` import가

   옮기면 해결된다.
2. 없는 APK 경로는 `FileNotFoundError`라 A의 `except StaticAnalysisError`에 안 걸리고
