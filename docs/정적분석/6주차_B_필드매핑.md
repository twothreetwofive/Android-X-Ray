## 0. 역할 문자 정리 (혼동 주의)

6주차부터 역할 번호와 A~D 문자를 통일했다.

| 6주차 역할 | 문자 | 담당 | 6주차 업무 |
|---|---|---|---|
| 역할 1 | A | 유예원 | 오케스트레이터 리드 (`main.py`, 통합 스펙) |
| 역할 2 | B | 왕은서 (본인) | 정적 분석 출력 정리 (어댑터 + 단위 테스트) |
| 역할 3 | C | 김은아 | 동적 분석 출력 정리 |
| 역할 4 | D | 백소정 | 네트워크 마무리 + 종합 위험도 점수 |

**주의**: `src/static_analyzer/` 각 파일 상단 주석의 "(A 작성)", "(C 작성)", "(원래 D 담당)"
표기는 **3주차 당시의 역할 문자**라 위 표와 다르다. 5주차 네트워크 모듈의 A~D도 또 다른
배정이었다. 코드 주석의 문자는 "그때 그 사람"이라는 이력 표시로만 읽고, 6주차 담당은
위 표를 기준으로 한다.

## 1. 이 문서를 쓴 이유

6주차 계획서상 B의 Day 1 과제는 "역할 1(A)의 스펙에 맞추기 위한 필드 매핑"이다.
그런데 A의 6주차 통합 스펙은 아직 나오지 않았다.

대신 **1주차에 이미 팀이 합의한 스펙이 존재한다** — `schemas/static_report.schema.json`.
`schemas/README.md`에도 이렇게 못 박혀 있다:

> 각 모듈 구현 시(2주차~5주차) 이 스키마의 필드명을 그대로 사용해서 결과 JSON을 생성한다.
> (…) 임의로 필드명을 바꾸면 6주차 통합(`main.py` 오케스트레이터)에서 파싱 에러가 난다.

따라서 이 문서는 **`schemas/static_report.schema.json`을 목표 포맷으로 놓고** 매핑을
정리한다. A가 6주차에 다른 스펙을 확정하면 바뀌는 것은 어댑터의 출력부 한 곳뿐이므로,
지금 시작해도 손해가 없다.

그리고 실제로 대조해 보니 **현재 구현 출력과 1주차 팀 스키마가 서로 맞지 않는다.**
이름만 다른 수준이 아니라, 데이터가 아예 생성되지 않는 항목이 있다. 이 문서의 본론은
그 불일치 목록이다.

## 3. 필드별 매핑

### 3-1. `meta`

| 스키마 필드 | required | 현재 출처 | 상태 |
|---|---|---|---|
| `package_name` | O | `meta.package_name` | 그대로 사용 가능 |
| `apk_name` | O | **없음** | 생성 필요 |
| `analyzed_at` | O | **없음** | 생성 필요 |
| `sha256` | X | `meta.file_hash.sha256` | 경로만 변경 |
| `min_sdk` | X | `meta.min_sdk` | 그대로 |
| `target_sdk` | X | `meta.target_sdk` | 그대로 |

**문제 1 — `apk_name`을 어댑터가 알 수 없다.**
`analyze_static(apk_path, ...)`는 apk 경로를 인자로 받지만, 반환 dict 어디에도 파일명이나
경로를 담지 않는다. `extract_apk()`는 내부적으로 `apk_path`를 반환하지만
(`apk_extractor.py:64`), `analyzer.py:49`가 `extracted["meta"]`만 꺼내 쓰고 나머지는 버린다.
즉 **`analyze_static()`의 결과만 받아서는 어떤 파일을 분석한 건지 알 수 없다.**

- 방안 (a): 어댑터 시그니처를 `to_static_report(result, apk_path)`로 만들어 밖에서 받는다.
- 방안 (b): `extract_apk()`의 `meta`에 `apk_name`을 추가한다.
- **권장: (b).** 파일명은 APK 자체의 메타데이터라 `meta`에 있는 게 자연스럽고, 한 번 넣어두면
  어댑터뿐 아니라 나중에 대시보드(7~8주차)에서도 그대로 쓴다. 호출부에 인자를 계속
  들고 다니게 하는 (a)보다 낫다.

**문제 2 — `analyzed_at`(분석 실행 시각, ISO 8601)을 아무도 안 남긴다.**
어댑터에서 `datetime.now()`로 만들 수는 있지만, 그러면 "분석한 시각"이 아니라
"변환한 시각"이 된다. 분석과 변환 사이에 시간이 뜨면 값이 틀어진다.

- **권장: `analyzer.analyze_static()`이 분석 시작 시각을 찍어서 `meta.analyzed_at`에 넣는다.**
  네트워크 모듈이 `CaptureMeta.capture_started_at`을 캡처 시점에 기록하는 것과 같은 방식이다.

> `min_sdk` / `target_sdk`는 `_safe_int()`가 실패 시 `0`을 넣는다(`apk_extractor.py:27`).
> 스키마상 타입(integer)은 만족하지만 값 `0`은 "SDK 0"이 아니라 "파싱 실패"라는 뜻이므로,
> 대시보드에서 그대로 보여주면 오해를 준다. 어댑터에서 `0`을 `None`으로 바꿀지는
> A의 통합 스펙에서 null 허용 여부를 확인한 뒤 결정한다. (**A에게 질의할 항목**)

### 3-2. `permissions` — 문자열 배열 → 객체 배열

스키마 요구:
```json
{ "name": "android.permission.READ_SMS", "risk_level": "high", "abuse_example": "스미싱, 문자 탈취" }
```

현재 출력(`manifest_parser.py:62`):
```python
"permissions": ["android.permission.INTERNET", "android.permission.READ_SMS", ...]  # 문자열만
"dangerous_permissions": [...]  # PERMISSION_WEIGHTS >= 8 인 것만 따로
```

**`risk_level`과 `abuse_example`은 현재 어디에서도 생성되지 않는다.**

**`risk_level` 도출 방안** — `manifest_parser.PERMISSION_WEIGHTS`(1~10 스케일)를 구간으로 나눈다.
`dangerous_permissions` 필터가 이미 `>= 8`을 쓰고 있으므로(`manifest_parser.py:45`) 그 경계를
그대로 살린다:

| 가중치 | risk_level | 근거 |
|---|---|---|
| 8 이상 | `high` | 기존 `dangerous_permissions` 기준과 일치 |
| 4 ~ 7 | `medium` | |
| 3 이하 / 미등록 | `low` | `PERMISSION_WEIGHTS.get(p, 0)` → 0 |

**한계 (반드시 인지할 것)**: `PERMISSION_WEIGHTS`에 현재 **5개 권한밖에 없다.**
그래서 `READ_CONTACTS`, `ACCESS_FINE_LOCATION`, `CAMERA`, `RECORD_AUDIO` 같은 실제 위험
권한이 전부 미등록 → 가중치 0 → `low`로 나온다. 단순 `INTERNET`과 같은 등급이 되어버린다.
목록 확장이 필요하다.

> **D(백소정)에게 질의할 항목**: `PERMISSION_WEIGHTS`는 `risk_scorer.calculate_risk()`가
> 그대로 합산에 쓰는 표다(`risk_scorer.py:10,21`). B가 임의로 항목을 추가하면 **D의 위험도
> 점수가 통째로 바뀐다.** 따라서 목록 확장은 B가 단독으로 하지 않고, D의 6주차 종합 점수
> 설계와 함께 결정한다. Day 1~2 안에 D에게 전달할 것.

**`abuse_example` 방안** — 스키마상 `required`가 아니므로 없어도 검증은 통과한다. 다만 이
프로젝트의 최종 목표가 "일반 사용자가 앱의 위험 활동을 쉽게 확인하는 X-ray 앱"이므로,
권한명만 보여주는 것보다 "이 권한이 왜 위험한가"를 붙이는 게 기획 의도에 맞다.

- 위험도 점수와 무관한 **설명 텍스트**이므로 D와 충돌하지 않는다 → **B가 담당해도 안전.**
- `{권한명: 악용 예시}` 상수 dict로 두되, 위치는 `PERMISSION_WEIGHTS` 옆(`manifest_parser.py`)이
  자연스럽다. 6주차 계획서에서 "화이트리스트를 별도 파일로 분리하지 않고 코드 상수로 유지"하기로
  한 결정과도 일관된다.

### 3-3. `components` — 4개 리스트 → 단일 객체 배열

스키마 요구:
```json
{ "type": "receiver", "name": "com.x.BootReceiver", "exported": true,
  "intent_filters": ["android.intent.action.BOOT_COMPLETED"] }
```

현재 출력(`manifest_parser.py:61-68`):
```python
"activities": ["...", ...],   # 이름 문자열만
"services":   [...],
"receivers":  [...],
"providers":  [...],
"exported_components": [...]  # 4종류가 섞인 이름 문자열 목록
```

**문제 1 — `type`과 `exported`가 분리 저장돼 있다.**
`_get_component_info()`는 내부적으로 `{"name", "exported"}` 쌍을 만들지만
(`manifest_parser.py:35`), 반환 직전에 이름만 뽑아 4개 리스트로 흩고 exported 여부는
종류 구분 없이 한 리스트로 합쳐버린다(`manifest_parser.py:54-59`).

어댑터에서 역조립은 가능하다 — 4개 리스트를 순회하며 `type`은 리스트별로 정하고,
`exported`는 `name in exported_components`로 판정. 다만 **같은 클래스명이 서로 다른 종류로
중복 등록되거나 이름이 겹치면 판정이 섞인다.** 드물지만 원본 정보를 버렸기 때문에
어댑터 쪽에서는 구분할 방법이 없다.

**문제 2 — `intent_filters`는 어댑터로 절대 못 채운다.**
`manifest_parser.py:28`에서
```python
has_intent_filter = elem.find("intent-filter") is not None
```
**intent-filter의 존재 여부만 bool로 쓰고 내용은 읽지 않고 버린다.** exported 기본값을
추론하는 용도로만 쓰인다. 원본 `AndroidManifest.xml`에는 action/category가 다 들어있는데
파싱 단계에서 사라지므로, **`manifest_parser.py`를 고치는 것 외에 방법이 없다.**

이건 정적 분석 모듈 내부 작업이므로 6주차 B 범위가 맞다. 그리고 이 필드는 실질적으로 중요하다 —
`BOOT_COMPLETED`(부팅 시 자동 실행), `SMS_RECEIVED`(문자 수신 가로채기) 같은 값이
여기 들어있고, 우리가 분석했던 Anubis의 핵심 동작이 정확히 이 지점이다.

**권장 수정 방향**: `_get_component_info()`가 `{"name", "exported", "intent_filters"}`를
반환하도록 하고, `parse_manifest()`가 종류별 구조를 유지한 채 내보낸다. 기존 4개 리스트
필드는 다른 코드가 참조 중일 수 있으니 **일단 유지하고 구조화된 필드를 추가**하는 방향이
안전하다. (제거는 A의 통합 스펙 확정 후)

### 3-4. `risk_score` — float → 객체

스키마 요구:
```json
{ "total": 62.0, "scale": "0-100",
  "breakdown": [ { "permission": "android.permission.READ_SMS", "weight": 9 } ] }
```

현재 출력: `float` 하나 (0.0~1.0). `risk_scorer.py:34`에서
`min(raw / NORMALIZATION_CAP, 1.0)`으로 정규화된 값이다.

- `total`: `round(risk_score * 100, 1)`로 변환 가능 (`NORMALIZATION_CAP = 100.0`이라 사실상
  raw 점수를 되돌리는 셈이지만, 100 초과분은 clamp돼서 이미 잘려 있다).
- `scale`: `"0-100"` 고정 문자열.
- `breakdown`: **현재 생성되지 않는다.** `calculate_risk()`는 raw 점수를 누적만 하고 근거를
  남기지 않는다(`risk_scorer.py:19-32`).

**breakdown에 대한 판단**: 어댑터가 `manifest.dangerous_permissions`와 `PERMISSION_WEIGHTS`로
권한 항목만은 재현할 수 있다. 하지만 실제 raw 점수에는 권한 외에도
`exported_components × 2`, `suspicious_api_calls × 3`, 난독화 +15, 리플렉션 +10,
동적 로딩 +15, `suspicious_strings × 2`가 함께 들어간다. 따라서 **권한만 재현한 breakdown은
합계가 `total`과 맞지 않는다.** 스키마의 `breakdown` 설명이 "점수 계산 근거"인데
근거의 합이 총점과 다르면 오히려 혼란스럽다.

- **결론: `risk_score`는 D(백소정) 영역이므로 B가 `risk_scorer.py`를 고치지 않는다.**
  6주차 계획서상 종합 위험도 점수 로직은 D 단독 담당이고, `risk_scorer.py` 주석에도
  "원래 D 담당"이라 적혀 있다. 여기서 B가 손대면 Day 3~4에 충돌한다.
- 어댑터는 **`breakdown`을 생략**하고(스키마상 optional) `total`/`scale`만 채운다.
  `breakdown`은 D에게 "계산 근거를 반환값에 남겨달라"고 요청 사항으로 넘긴다.

**추가 문제** — `calculate_risk()`가 실패하면 `_run_stage()`가 `None`을 반환하고
`risk_score`는 `None`이 된다(`analyzer.py:46,64`). 그런데 스키마에서 `risk_score`는
`required`다. 어댑터가 `None`을 어떻게 처리할지 정해야 한다 (3-6절 참고).

### 3-5. 스키마에 자리가 없는 4개 필드

`certificate`, `code_analysis`, `strings`, `third_party_sdks`는 1주차 스키마 작성 시점에
고려되지 않았다. 버리기엔 아까운 정보가 섞여 있다.

| 필드 | 버리면 안 되는 이유 | 관련 역할 |
|---|---|---|
| `code_analysis` | 난독화/리플렉션/동적 코드 로딩 여부는 D의 종합 점수가 쓸 가능성이 높다 (이미 `risk_scorer`가 내부적으로 쓰고 있음) | D |
| `strings` | `urls` / `ip_addresses`가 **네트워크 모듈의 `suspicious.domains` / `suspicious.ips`와 직접 대조 가능**하다. "코드에 하드코딩된 주소가 실제 트래픽에도 나타났는가"는 정적+네트워크를 엮는 가장 강력한 근거이고, 통합 리포트의 핵심 볼거리가 될 수 있다 | D, A |
| `certificate` | `is_self_signed`는 그 자체로 위험 신호 | D |
| `third_party_sdks` | 정상 앱 판별의 맥락 정보 (광고 SDK 트래픽 = 네트워크 화이트리스트와 연결됨) | D |

- **권장: A의 통합 스펙에 이 4개 필드 자리를 만들어 달라고 제안한다.**
  통합 리포트 최상위에 정적 분석 원본을 그대로 실어도 되고, `static_report.schema.json`을
  확장해도 된다. `schemas/README.md`에도 "실제 구현하면서 필드가 부족하거나 불필요하면
  팀 논의 후 수정 가능"이라고 열어두었다.
- 그때까지 어댑터는 이 4개를 **손실 없이 통과시키되(pass-through) 스키마 검증 대상에서는
  제외**하는 형태로 둔다.

---

### 3-6. `errors` — 통합에서 가장 중요한데 스키마에 없음

`analyze_static()`은 부분 실패를 예외로 던지지 않고 `errors` 리스트에 문자열로 쌓은 뒤
정상 반환한다(`analyzer.py:60-64`). 즉 **하위 6개 단계 중 무엇이 실패해도 `analyze_static()`은
성공한 것처럼 dict를 돌려준다.** 실패한 단계의 값은 `None`이다.

이건 어댑터 입장에서 두 가지를 뜻한다:

1. **어댑터는 모든 필드에 `None`이 올 수 있다고 가정하고 방어해야 한다.**
   특히 `manifest`가 `None`이면 스키마 required인 `permissions`와 `components`를 못 만든다.
2. **`errors`는 A의 오케스트레이터에 반드시 전달돼야 한다.** 6주차 계획서상 A의 Day 1 과제가
   "에러/타임아웃 처리 정책"인데, 정적 분석의 부분 실패는 예외가 아니라 이 리스트로만
   드러나기 때문이다. 이 사실을 모르면 A는 "정적 분석은 성공했다"고 판단하게 된다.

- **A에게 최우선으로 전달할 항목.** 통합 스펙에 모듈별 `errors`(또는 동등한 부분 실패 채널)
  자리를 반드시 넣어야 한다.
- `manifest`가 `None`일 때 어댑터 동작은 A의 정책에 달렸다:
  (a) 빈 배열로 채우고 `errors`에 맡긴다 / (b) 어댑터가 예외를 던져 통합을 중단시킨다.
  **B의 1차안은 (a)** — 정적 분석 모듈 전체가 "부분 실패해도 계속 진행" 정책으로 짜여 있으므로
  어댑터만 정책을 뒤집으면 일관성이 깨진다. (**A에게 확인할 항목**)

## 5. 다른 역할에게 넘길 항목

### A(유예원, 오케스트레이터)에게

1. **`errors` 전달 경로를 통합 스펙에 반드시 넣어달라.** 정적 분석은 부분 실패 시 예외를
   던지지 않고 정상 반환하므로, 이게 없으면 실패를 감지할 수 없다. (3-6절)
2. `manifest` 파싱 실패로 `permissions`/`components`를 만들 수 없을 때, 어댑터가
   **빈 배열 반환(B의 1차안)**인지 **예외 발생**인지 정책을 정해달라.
3. `min_sdk`/`target_sdk` 파싱 실패값 `0`을 그대로 둘지 `null`로 바꿀지 (null 허용 여부).
4. `certificate` / `code_analysis` / `strings` / `third_party_sdks` 4개 필드를 통합 리포트에
   실을 자리를 만들어달라. (3-5절)

### D(백소정, 종합 위험도 점수)에게

1. **`PERMISSION_WEIGHTS`(`manifest_parser.py:10`)에 현재 권한이 5개뿐이다.**
   `READ_CONTACTS`, `ACCESS_FINE_LOCATION`, `CAMERA`, `RECORD_AUDIO` 등이 빠져 있어 전부
   `low`로 분류된다. 확장이 필요한데 **이 표는 D의 `calculate_risk()`가 그대로 합산에 쓰므로,
   B가 임의로 늘리면 D의 점수가 바뀐다.** 6주차 종합 점수 설계와 함께 결정하자.
2. **`risk_score.breakdown`(점수 계산 근거)을 `calculate_risk()`가 반환값에 남겨달라.**
   어댑터에서 권한 항목만 재현하면 합계가 총점과 안 맞아 오히려 혼란스럽다. (3-4절)
3. 종합 점수에 정적 분석의 `code_analysis`(난독화/리플렉션/동적 로딩), `certificate.is_self_signed`,
   `strings.suspicious_strings`를 쓸 계획인지 알려달라. 쓸 거면 어댑터에서 버리지 않고
   통과시키겠다.
4. `strings.urls` / `strings.ip_addresses`를 네트워크 모듈의 `suspicious.domains` /
   `suspicious.ips`와 대조하는 것을 제안한다. "코드에 하드코딩된 주소가 실제 트래픽에도
   나타났는가"는 정적·네트워크를 잇는 강한 근거다.

### C(김은아, 동적 분석 출력 정리)에게

- 동적 모듈(`src/dynamic_analyzer/schema.py`)도 `schemas/dynamic_report.schema.json`과
  같은 종류의 불일치가 있을 가능성이 높다. 정적 쪽은 8개 필드 중 4개가 스키마에 자리가
  없었다. 어댑터 작성 전에 **구현 출력과 1주차 스키마를 먼저 대조**해보길 권한다.
