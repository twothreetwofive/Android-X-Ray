# 5주차 과제_D (1)

**사람**: 은서 (본인)

역할 분배(`docs/네트워크분석/네트워크 분석 모듈 개발 역할 분배.txt` — 아직 미작성,
대화로만 합의된 상태) 기준 D 역할 — 화이트리스트 구축 + 의심 도메인/IP 판별 +
`network_report.json` 최종 조립.

| 역할 | 담당 | 내용 |
|---|---|---|
| A | 은아 | tcpdump 캡처 자동화 (`packet_capturer.py`) |
| B | 소정 | DNS 파싱 (`dns_parser.py` → `dns_queries`) |
| C | 예원 | TLS SNI 파싱 (`sni_parser.py` → `tls_sni`) |
| D | 은서 (본인) | 화이트리스트 + 판별 로직 + 최종 조립 |

코드는 `main` 브랜치 `src/network_analyzer/`에 있음: `schema.py`,
`exceptions.py`, `whitelist_checker.py`.

이 보고서는 D의 1~2일차 작업만 다룬다. A/B의 실제 캡처 데이터가 필요한
3일차 이후 작업은 다음 보고서(`5주차보고서(2)`)에서 다룰 예정.

---

## 1일차 — 화이트리스트 소스 조사 + 스켈레톤

A/B/C의 3일차 인수인계 전이라, pcap이나 파서 출력 없이도 만들 수 있는
부분부터 시작. D 작업은 `dns_queries`/`tls_sni` 배열(문자열 도메인 목록)만
입력으로 받으면 되기 때문에, A/B/C 코드가 하나도 없어도 온전히 독립적으로
진행 가능했음.

- `schema.py`: `schemas/network_report.schema.json`을 그대로 TypedDict로
  옮김 (`NetworkAnalysisResult`, `CaptureMeta`, `DnsQuery`, `TlsSni`,
  `Suspicious`, `SuspiciousDomain`, `SuspiciousIP`). 정적/동적 모듈의
  `schema.py`와 같은 패턴 — "팀 공유 계약" 주석을 그대로 유지해서, 필드를
  바꾸려면 JSON 스키마부터 고치고 팀에 공유하도록 못 박아둠.
- `exceptions.py`: `NetworkAnalysisError` — static/dynamic 모듈과 동일한
  패턴(치명적 에러만 예외로, 부분 실패는 결과의 `errors` 리스트로).
- 화이트리스트 도메인 조사: 발표 자료에서 "구글/광고 SDK 등"으로만
  언급됐던 부분을 실제 목록으로 구체화. 카테고리 4개로 정리:
  1. Google / Play services / Firebase (`googleapis.com`,
     `firebaseinstallations.googleapis.com`, `crashlytics.com`,
     `connectivitycheck.gstatic.com` 등 — 특히 마지막 두 개는 OS 자체의
     캡티브 포털/크래시 리포팅 체크라 앱 로직과 무관하게 항상 나타남)
  2. 광고 SDK (Unity Ads, AppLovin, AdColony, Vungle, ironSource,
     Chartboost, MoPub, Facebook Audience Network)
  3. 분석/크래시 리포팅 (Amplitude, Mixpanel, Sentry, Flurry, OneSignal)
  4. CDN (Cloudflare, CloudFront, Akamai, Fastly) — 정상 앱도 리소스를
     CDN에서 받아오는 경우가 많아 도메인만 보면 오탐 가능성이 높은 카테고리

## 2일차 — 화이트리스트 1차 목록 확정 + 판별 규칙 설계

- `whitelist_checker.py` 완성:
  - `is_whitelisted(domain)`: 화이트리스트 도메인과 정확히 같거나, 그
    서브도메인(`*.googleapis.com` 형태)이면 `True`. 문자열 `in` 대신
    `==` / `endswith("." + entry)`로 비교 — 안 그러면
    `evil-googleapis.com.attacker.net` 같은 도메인이 `googleapis.com`을
    부분 문자열로 포함한다는 이유만으로 화이트리스트를 통과하는 우회가
    가능해짐.
  - `find_suspicious_domains(domains)`: 입력 도메인 목록에서 중복을
    제거하고, 화이트리스트에 없는 도메인만
    `{"domain": ..., "reason": "화이트리스트 미포함"}` 형식으로 반환.
    `schemas/network_report.schema.json`의 `suspicious.domains` 항목
    형식과 그대로 맞춤.
- 동작 확인: `googleapis.com`류 도메인은 걸러지고, 임의 도메인만
  `suspicious`로 분류되는 것을 스크립트로 검증함 (실제 pcap 데이터는
  아직 없어서 하드코딩한 도메인 목록으로 테스트).

## 아직 안 한 것

- ⬜ **IP 기반 의심 판별** (`suspicious.ips`, "하드코딩된 IP 패턴") — 4일차
  범위로 남겨둠. 판별 기준(예: 지리적으로 이상한 위치, 알려진 클라우드
  호스팅 IP 대역 여부 등)을 아직 정하지 않았음 — 팀 논의 필요.
- ⬜ **실제 캡처 데이터로 검증** — A의 `capture.pcap`, B/C의
  `dns_queries`/`tls_sni` 실제 출력이 나와야 화이트리스트가 실전에서
  얼마나 정확한지 확인 가능 (3일차 인수인계 이후).
- ⬜ 화이트리스트는 1차 목록이라 완전하지 않음. 실제 캡처 결과에서
  정상 트래픽인데 걸러지지 않는 도메인이 나오면 팀과 상의해서 추가.

## 팀 논의 필요

- IP 기반 판별 규칙을 어떤 기준으로 잡을지 (4일차 착수 전에 정해야 함).
- 화이트리스트 파일을 코드에 하드코딩(`WHITELIST_DOMAINS`)해둔 상태인데,
  나중에 팀원이 도메인을 추가/삭제하기 편하도록 별도 파일(JSON/YAML)로
  분리할지 — 정적 분석의 위험 권한 딕셔너리처럼 코드 내 상수로 유지해도
  될지 상의 필요.
