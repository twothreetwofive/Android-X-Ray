**사람**: 은서 (본인)

`5주차보고서(1).md`에서 이어지는 D 3~4일차 작업. A/C가 5주차에 실제로 캡처/파싱을

## 3일차 — IP 기반 의심 판별 (`suspicious.ips`)

1~2일차 보고서에서 "판별 기준을 아직 안 정했다"고 남겨뒀던 부분. A의 5주차 캡처
결과를 보고 기준을 정했다.

### A의 캡처에서 얻은 힌트

A가 `com.google.android.calendar`로 실제 캡처를 두 번 돌렸는데, 앱-에뮬레이터
내부 통신이 전부 `127.0.0.1` 루프백으로 잡혀서 `dns_queries`/`tls_sni`가 비어
있었다(`tshark -q -z conv,tcp` 결과 두 커넥션 모두 `127.0.0.1 <-> 127.0.0.1`).
이걸 보고 "사설/루프백 IP까지 suspicious로 잡으면 이런 정상 로컬 트래픽이
전부 오탐 처리되겠다"는 걸 확인했고, 그래서 첫 번째 규칙을 이렇게 정했다.

### 판별 규칙 (1차)

1. **사설/루프백/링크로컬/멀티캐스트/예약 대역은 제외한다.** Python 표준 라이브러리
   `ipaddress` 모듈의 `is_private`/`is_loopback`/`is_link_local`/`is_multicast`/
   `is_reserved`로 판별 (`ip_checker.py`의 `_is_internal`). 외부 IP 데이터베이스나
   추가 의존성 없이 표준 라이브러리만으로 처리 가능해서 이 방식을 택함.
2. **남은 공인 IP는 1차로 전부 "하드코딩된 직접 접속 후보"로 의심 처리한다.**
   정상 앱은 보통 DNS로 도메인을 조회한 뒤 접속하니까, `resolved_ip`/`dest_ip`에
   IP만 있고 대응하는 도메인이 없다는 것 자체가 의심 신호라고 판단했다.
   다만 이 규칙은 공인 IP면 전부 걸리는 거라 오탐이 많을 수 있는 1차 버전이고,
   CDN/클라우드 사업자 IP 대역 화이트리스트는 아직 없다 (아래 "아직 안 한 것" 참고).

### 예상 못한 부분 — TEST-NET 대역이 `is_private`로 잡힘

검증 코드를 짜다가 `203.0.113.7`(RFC 5737 TEST-NET-3, 문서 예제용으로 예약된
대역)을 공인 IP 예시로 넣었는데, Python `ipaddress`가 이걸 `is_private=True`로
분류해서 사설 IP와 동일하게 걸러진다는 걸 발견했다 (`8.8.8.8`, `1.1.1.1`처럼
실제 라우팅되는 IP만 규칙 2에 걸림). `ip_checker.py` 검증 코드 하단 주석에 이유를
남겨뒀다 — 나중에 팀원이 테스트용 IP를 고를 때 예약 대역을 실제 공인 IP로
착각하지 않도록.

### 도메인 판별과의 연결 — "하드코딩된 형태"

`schema.py`의 `SuspiciousDomain.reason` 주석에는 원래 "화이트리스트 미포함",
"하드코딩된 형태" 두 가지 예시가 있었는데, 1~2일차에는 "화이트리스트 미포함"만
구현돼 있었다. 이번에 `is_ip_literal()`(도메인/SNI 필드에 호스트명 대신 IP가
그대로 들어있는지 확인)을 추가하고, `whitelist_checker.py`의
`find_suspicious_domains()`가 이걸 먼저 체크하도록 고쳐서 "하드코딩된 형태"
케이스를 채웠다. TLS SNI나 DNS 쿼리 도메인 필드에 IP가 그대로 들어있는 건
정상적인 상황이 아니라서 (SNI는 항상 호스트명이어야 함) 화이트리스트 미포함과
구분해서 표시한다.

## 4일차 — 최종 조립 (`report_builder.py`)

README 표에 있는 D 역할 세 개 중 마지막 "최종 조립"을 구현했다.

- `build_network_report(meta, dns_queries, tls_sni)`: A/B/C가 만드는
  `CaptureMeta`/`DnsQuery`/`TlsSni` 그대로 받아서, `dns_queries`의 `domain`과
  `tls_sni`의 `sni`를 합쳐 `find_suspicious_domains()`에, `resolved_ip`와
  `dest_ip`를 합쳐 `find_suspicious_ips()`에 넘기고 `schema.py`의
  `NetworkAnalysisResult` 형식으로 조립해서 반환한다.
- `dns_queries`/`tls_sni`가 빈 리스트여도(캡처 실패, B/C 미통합 등) 그대로
  빈 `suspicious`를 반환하고 에러 없이 끝난다 — A의 실제 캡처에서 이 상황이
  실제로 나왔기 때문에 (`Scenario error`는 없었지만 `dns_query_count`/
  `tls_sni_count`가 0), 빈 입력을 예외 상황이 아니라 정상 케이스로 다뤄야
  한다고 판단했다.

### 검증에 쓴 데이터

B/C의 `dns_parser.py`/`sni_parser.py`가 아직 이 브랜치에 통합되지 않아서
실제 파이프라인 산출물로는 검증하지 못했다. 대신 C가 SNI 구조를 학습하면서
실제로 캡처한 도메인 목록(`유예원_5주차_C.pdf`, 1일차 — 본인 PC에서 tshark로
직접 뜬 것)을 `report_builder.py` 검증 코드에 그대로 넣었다. 이건 우리 안드로이드
앱 트래픽이 아니라 일반 PC 트래픽이라 화이트리스트 최종 확정용 데이터는 아니지만,
실제 SNI 목록이 파이프라인을 어떻게 통과하는지 확인하는 용도로는 충분했다.

결과: `www.google.com`/`www.googleapis.com`/`www.googleusercontent.com`처럼
화이트리스트에 있는 도메인은 정상적으로 걸러지고, `github.com`/`velog.io`/
`www.inflearn.com`/마이크로소프트 계열 도메인(`login.microsoftonline.com`,
`outlook.office.com` 등) 13개가 `suspicious.domains`로 나왔다 — 전부 화이트리스트에
없는 정상 도메인이라 "필터링 로직이 도메인을 제대로 걸러내는지"는 확인됐지만,
동시에 "지금 화이트리스트는 구글/광고 SDK 중심이라 마이크로소프트나 개발자
커뮤니티 사이트 같은 일반 정상 도메인은 다 의심으로 뜬다"는 것도 확인했다.
실제 안드로이드 앱이 이런 도메인들과 통신할 일은 흔하지 않을 것 같지만
(웹뷰로 로그인 페이지를 띄우는 경우 등은 가능), B/C의 실제 앱 캡처 데이터가
나오면 화이트리스트에 오탐이 얼마나 나는지 다시 확인이 필요하다.

## 아직 안 한 것 / 팀 논의 필요 (유지)

- ⬜ **실제 우리 앱 캡처 데이터로 전체 파이프라인 검증**: A의 실제 캡처는 루프백만
  잡혀서 `dns_queries`/`tls_sni`가 비어 있었다 (A 5주차 보고서의 "패킷은 있는데
  DNS/TLS: 0 문제" 참고 — A가 원인 후보 3가지를 정리해뒀음). B/C의 파서가 이
  브랜치에 통합되고, A 쪽 캡처 이슈가 해결돼서 실제 `dns_queries`/`tls_sni`가
  나와야 `build_network_report()`와 화이트리스트를 실전 데이터로 검증할 수 있다.
- ⬜ **CDN/클라우드 IP 대역 화이트리스트**: 지금 `find_suspicious_ips()`는
  "사설이 아닌 공인 IP면 전부 의심"이라 오탐이 많을 수 있는 1차 규칙이다.
  실제 캡처에서 CDN/클라우드 IP가 계속 걸리면 대역 화이트리스트 추가를 논의해야
  한다.
- ⬜ 화이트리스트 자체는 여전히 1차 목록. C의 실제 캡처에서 나온 것처럼
  마이크로소프트/개발자 커뮤니티류 도메인을 어디까지 화이트리스트에 넣을지는
  실제 앱 캡처 결과를 보고 다시 상의.
