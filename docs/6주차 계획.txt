## 5주차에서 넘어온 미해결 항목 (6주차 Day 1에서 정리)

- [ ] **실제 앱 캡처 데이터로 검증** — A의 캡처 이슈가 해결돼서 실제 DNS 트래픽이
잡혀야, 지금 합성 데이터로만 확인한 로직이 실전에서도 맞는지 검증 가능하다.
- [ ] **실제 캡처 데이터로 화이트리스트 검증** — `capture.pcap`, 실제 `dns_queries`/
`tls_sni` 출력이 나와야 화이트리스트가 실전에서 얼마나 정확한지 확인 가능.
- [ ] 화이트리스트는 1차 목록이라 완전하지 않음. 실제 캡처 결과에서 정상 트래픽인데
걸러지지 않는 도메인이 나오면 발견 즉시 추가 (아래 "팀 논의 없이 결정" 참고).

## 팀 논의 없이 담당자가 결정 (더 이상 "팀 논의 필요"로 남겨두지 않음)

이전 계획에는 아래 두 가지가 "팀 논의 필요" 항목으로 남아있었지만, 통합 단계부터는
각 역할 담당자가 논의 없이 정한 대로 진행하고 결과만 공유하기로 함.

1. **IP 기반 의심 판별 기준**: 현재 git에 반영된 1차 규칙을 6주차에도 그대로 유지한다.
    - 사설/루프백/링크로컬/멀티캐스트/예약 대역은 제외 (`ipaddress` 표준 라이브러리의
      `is_private`/`is_loopback`/`is_link_local`/`is_multicast`/`is_reserved`로 판별).
    - 남은 공인 IP는 전부 "하드코딩된 직접 접속 후보"로 의심 처리.
    - 지리적 위치나 클라우드 호스팅 IP 대역까지 따지는 정교화는 6주차 범위 밖으로 명시적으로
      보류한다 (오탐 감수). 외부 IP 데이터베이스 연동이 필요한 작업이라 8주 로드맵 안에서
      우선순위가 낮다고 판단.
2. **화이트리스트 저장 방식**: 별도 JSON/YAML 파일로 분리하지 않고 코드 상수
   (`WHITELIST_DOMAINS`)로 유지한다. 정적 분석의 위험 권한 딕셔너리도 같은 방식이라
   일관성을 맞췄고, 파일 분리는 나중에 필요해지면 하는 리팩토링 과제로 미룬다.

## 6주차 목표

1. 정상 앱 1개로 네트워크 파이프라인(캡처→DNS/SNI 파싱→화이트리스트/IP 판별→리포트 조립)
   end-to-end 실행, `network_report.json` 최종 검증.
2. 정적→동적→네트워크 파이프라인 통합 (`main.py` 오케스트레이터), 종합 위험도 점수 로직 확정.

## 역할 분배 원칙

지금까지의 "완전 독립 역할 분담"은 개별 모듈 개발에는 잘 맞았지만, 통합·스코어링 단계는
성격이 달라서 오너 1명(허브) + 나머지는 각자 영역 정리 구조로 바꾼다.

- **오케스트레이터 통합**은 정적/동적/네트워크를 하나로 엮는 상호 의존적 작업이라 1명이
  메인으로 진행하고, 나머지는 자기 모듈 출력을 통합 스펙에 맞게 정리하는 역할을 맡는다.
- **종합 위험도 점수 로직**도 여러 명이 나누면 기준(가중치, 임계값)이 파편화되므로 1명이
  전담한다. 가중치 배분(예: static 40% / dynamic 35% / network 25%)은 코드를 짜는
  담당자가 1차안을 정하고 진행하며, 이견이 있으면 그때 가서 조정한다.

## 역할별 담당

**역할 1 — 오케스트레이터 리드**
- `main.py` 전체 흐름 설계 및 구현 (실행 순서, 모듈 간 데이터 전달, 에러/타임아웃 처리)
- 통합 인터페이스 스펙(입출력 JSON 포맷 등) 확정하고 나머지 역할에게 공유
- 전체 파이프라인 취합·디버깅의 허브 역할

**역할 2 — 정적 분석 출력 정리**
- 기존 `static_analyzer` 결과를 오케스트레이터 스펙에 맞게 어댑터/변환 코드 작성
- 정적 분석 데이터가 오케스트레이터에 올바르게 들어가는지 단위 테스트

**역할 3 — 동적 분석 출력 정리**
- `dynamic_report.json` 결과를 통합 스펙에 맞게 변환
- 동적 분석 쪽 타이밍 이슈(레이스 컨디션)가 있을 수 있으니 오케스트레이터의
  타임아웃/재시도 로직을 역할 1과 함께 검증

**역할 4 — 네트워크 마무리 + 위험도 점수 로직 오너**
- 5주차에서 넘어온 네트워크 모듈 잔여 항목(실제 캡처 검증, e2e 확인) 마무리
- 정적/동적/네트워크 3개 모듈 출력을 받아 종합 점수 계산하는 로직 구현
  (가중치 1차안 포함, 임계값 설계 포함)

## 일정 (5~6일 분량)

**Day 1**
- 역할 1: 통합 인터페이스 스펙 초안 작성 (3개 모듈 출력 통합 방식, 실행 순서, 에러/타임아웃
  처리 정책) 및 공유
- 역할 4: 네트워크 잔여 항목 착수 — 실제 캡처 재시도, 안 되면 기존 샘플 데이터로 1차 검증
  진행. 위 "팀 논의 없이 결정" 두 건은 그대로 적용하고 코드/문서에 근거만 남김
- 역할 2: 정적 분석 8개 필드를 역할 1의 스펙에 맞추기 위한 필드 매핑 정리
- 역할 3: `dynamic_report.json` 출력을 역할 1의 스펙에 맞추기 위한 필드 매핑 정리,
  타이밍 이슈 케이스 정리

**Day 2**
- 역할 1: `main.py` 골격 작성 (오케스트레이터 함수 시그니처, 모듈 호출 순서, 예외 처리 골격)
- 역할 4: 네트워크 e2e 1차 결과로 `network_report.json` 스키마 검증, 위험도 가중치 1차안 제시
- 역할 2 / 역할 3: 각자 어댑터 코드 작성 착수

**Day 3 — 인수인계 데드라인**
- 역할 1: `main.py` 골격을 역할 2/3/4에게 전달 (각자 어댑터를 꽂아볼 수 있는 상태로)
- 역할 2: 정적 어댑터 완성, 골격에 연결해서 단위 테스트
- 역할 3: 동적 어댑터 완성, 골격에 연결해서 단위 테스트 (타이밍 이슈 검증 포함)
- 역할 4: 위험도 점수 로직 구현 착수 (1차 가중치 기준으로)

**Day 4**
- 역할 1: 역할 2/3/4 결과물 취합해서 전체 파이프라인 1차 실행, 에러 로그 확인
- 역할 4: 위험도 점수 로직 완성 (3개 모듈 출력 반영), 위험 구간(고/중/저) 임계값 설계
- 역할 2 / 역할 3: 취합 과정에서 나온 버그 수정, 인터페이스 불일치 대응

**Day 5**
- 전원: 정상 앱 1개로 전체 파이프라인 end-to-end 실행, static/dynamic/network 3개 리포트가
  모여 종합 리포트가 정상적으로 나오는지 확인
- 버그 수정, 발표자료(실행 로그/캡처) 준비

**Day 6 (버퍼, 필요시에만)**
- 미해결 이슈 마무리, README 갱신, 발표자료 다듬기

## 작업 비중

**역할 1 (오케스트레이터 리드) > 역할 4 (네트워크 마무리 + 위험도 점수) > 역할 2 ≈ 역할 3**

- 역할 1이 가장 무겁다: 통합 스펙을 처음부터 설계해야 하고, Day 3 이후 전체 취합·디버깅
  허브 역할까지 맡아서 일정 내내 부담이 이어진다.
- 역할 4가 두 번째로 무겁다: 5주차부터 이어진 네트워크 모듈 마무리(실제 캡처 검증)를
  떠안은 상태에서, 종합 위험도 점수라는 새 로직까지 단독으로 설계·구현해야 한다.
- 역할 2, 역할 3은 상대적으로 가볍다: 이미 완성된 모듈 결과를 정해진 스펙에 맞게
  변환하는 어댑터 작업이 중심이라 새로 설계할 부분이 적다.
