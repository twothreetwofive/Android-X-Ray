**기간**: 2026-08-11 ~ 8주차 발표일
**기준 커밋**: `origin/main` = `f33df91` (7주차 A/B/C/D 전원 병합 완료 시점)
**목표 한 줄**: 격리 네트워크 환경에서 실제 뱅킹 악성코드 샘플로 엔드투엔드 테스트 → 버그 수정 → 수동 분석 대비 시간 단축 정량화

## 0. 시작 시점 상태 진단

### 된 것

| 구성 요소 | 상태 |
|---|---|
| 오케스트레이터 (`src/main.py`) | 3모듈 통합 + 부분 리포트 정책 + `on_progress` 콜백 |
| 대시보드 골격 (`app.py`/`common.py`/`pipeline_bridge.py`) | 업로드 → 실행 → 4탭 |
| 정적 뷰 (`views/static_view.py`) | 구현 + 테스트 51개 |
| 동적 뷰 (`views/dynamic_view.py`) | 구현 |
| 네트워크 뷰 / 종합 위험도 (`views/network_view.py`, `risk_view.py`) | 구현 |
| 종합 스코어링 (`src/risk_aggregator.py`) | 구현 + `main.py` 배선 |
| 테스트 | pytest 118개 통과 (전부 정적 계열) |

### 안 된 것 — 8주차가 메워야 할 공백

- **실제 APK로 파이프라인이 끝까지 성공한 적이 없음.** C의 7주차 기록 기준 도달점: 정적 통과 → Frida 연결 → **tcpdump 에러에서 중단**
- 화면에 표시된 값은 **전부 수작업 샘플** (정적 샘플 4종, 리스크 더미). `risk_view`는 `total=None`이면 "예시 데이터" 배너 표시 상태
- 점수 상수 전부 미검증 추정값
  - `risk_scorer.NORMALIZATION_CAP = 100` → 흔한 뱅킹 트로이목마 구성만으로 raw 140 → **100점에서 잘림** (7주차 B 4-(2))
  - `risk_aggregator.MODULE_WEIGHTS` 0.4/0.3/0.3, `LEVEL_THRESHOLDS` 0.34/0.67 — 실샘플 미검증
- 격리 네트워크 환경 **미구축** (2주차 발표자료 리스크 항목에만 존재)
- 수동 분석 시간 **기록 없음** — 3~6월 분석은 학습 시간이 섞여 있어 그대로 baseline으로 못 씀

### 환경 편차 — 8주차 최대 리스크

- C(Windows): apktool / jadx / Frida / 에뮬레이터 보유 → **파이프라인 전체를 돌릴 수 있는 유일한 기준 PC**
- B: apktool / jadx 없음, 정적 로직·테스트만 가능
- 대응: **기준 PC를 C로 못박고**, 나머지는 기준 PC 산출물(report.json, pcap)을 받아 각자 파트를 검증한다. 6주차의 "서로 기다리다 아무것도 못 함" 재발 방지가 목적

## 1. 격리 네트워크 환경 구성 (Day 1, C 주관 / D 협조)

### 필수 조건

1. **전용 에뮬레이터 AVD** — 개인 계정·연락처·사진이 없는 신규 AVD. 실기기 사용 금지
2. **스냅샷 백업** — 샘플 설치 **전** 스냅샷 저장, 1회 실행마다 스냅샷 복원. 감염 상태 누적 방지
3. **호스트 격리** — 가능하면 별도 VM. 최소한 호스트의 공유 폴더/클립보드 연결 해제
4. **샘플 취급** — 확장자 변경(`.apk` → `.apk_`) + 압축 보관, 저장소에 커밋 금지(`.gitignore` 확인)

### 트래픽 정책 — 판단 필요 (D 결정)

완전 차단하면 관측할 트래픽 자체가 사라지므로, 두 모드를 구분해서 돌린다.

| 모드 | 구성 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| **A. sinkhole** | DNS는 내부에서 응답, TCP는 전부 drop | `dns_queries` 확보, C2 도메인 판별 가능, 외부 유출 없음 | `tls_sni` 비게 됨 (핸드셰이크 미성립) |
| **B. 제한적 실통신** | 실제 인터넷 허용, 대신 별도 VM/전용 회선 | `tls_sni`까지 확보 → 네트워크 뷰 전체 검증 | 실제로 C2에 접속하게 됨 |

- **권장: A를 기본으로 하고, B는 하지 않는다.** 학부 프로젝트 범위에서 실제 C2 접속은 정당화하기 어려움
- 모드 A에서 `tls_sni`가 비는 것은 **결함이 아니라 환경 제약**이므로, 발표 자료와 리포트에 그 사실을 명시한다
- SNI 화면 검증이 필요하면 정상 앱(예: 공개 오픈소스 앱)을 모드 B 없이 일반 환경에서 돌려 별도 확보

### 샘플

- 1순위: 3~6월에 이미 분석한 `anubis.apk`, `syssecapp.apk` — **이미 손에 있고 수동 분석 경험이 있어 baseline 비교가 가능**한 것이 결정적
- 대조군: 정상 앱 2개 (권한 구성이 대비되도록 — 예: 계산기류 1개, 메신저류 1개)
- 확장이 필요하면 MalwareBazaar (`docs/anubis_공개샘플_조사.md` 참고). 다만 **8주차 안에 새 샘플 확보는 선택 사항**으로 두고, 확보 실패해도 일정이 안 흔들리게 함

## 2. 역할 분담

### A — 유예원 (오케스트레이터 / 계측)

1. **단계별 소요시간 계측을 `run_pipeline`에 추가** ← 정량화의 자동 측정치 공급원
   - `report["timing"] = {"static_sec": …, "dynamic_network_sec": …, "risk_sec": …, "total_sec": …}`
   - 이미 있는 `_notify(on_progress, stage, status)` 지점에서 시각을 찍으면 되므로 구조 변경 불필요
   - B의 정량화 표가 이 필드를 그대로 소비하므로 **Day 2 전까지 필요**
2. `outer timeout` 트립 시 adb/frida 좀비 프로세스 정리 (6주차부터 이월, `main.py` 상단 주석에 명시된 미해결 항목)
3. e2e 중 오케스트레이터 계층에서 나오는 버그 수정 (모듈 경계·예외 처리)
4. **(A-1 회신)** `views/`에서 `src/`를 import하는 방법 확정
   - 현재 `views/static_data.py`가 스스로 `sys.path` 조작 중. C/D도 따라하면 3벌이 됨
   - `views/__init__.py`에 한 번만 두고 각 뷰의 중복 제거를 권장. A 소유 파일이라 A가 결정

### B — (본인, 정적 / 검증 / 정량화)

1. **수동 분석 대비 시간 단축 정량화** (3장 참조) — 설계·측정·표 작성 주관
2. 기준 PC의 실측 `report.json`을 받아 **정적 탭 실측 검증**
   - 지금까지 화면에 띄운 값은 전부 수작업 샘플. 실제 `analyze_static()` 출력에서 필드가 비거나 형태가 다른 경우를 확인
   - 필드 누락이 발견되면 `views/static_data.py`의 방어 로직 보강 + 회귀 테스트 추가
3. **잔 버그 정리** (4장 목록의 1·2·3·5번)
4. 발표 자료용 화면 캡처 — **더미 배너가 뜬 상태의 화면은 캡처 금지**
5. 8주차 보고서

### C — 김은아 (동적 / 기준 PC)

1. **격리 환경 구축** (1장) — AVD·스냅샷·호스트 격리, 구성 절차를 문서로 남겨 다른 팀원이 재현 가능하게
2. **Frida 안정화** — 샘플 실행 시 크래시/후킹 누락 대응. Anubis 계열은 에뮬레이터 탐지·루팅 탐지로 조기 종료할 수 있으므로, 그 경우 `crashed` 플래그가 대시보드에 제대로 뜨는지까지 확인 (실패해도 화면이 안 죽는 것이 7주차 검증 포인트였음)
3. **실샘플 e2e 실행 담당** — 정상 2개 + 악성 2개, 각 3회 반복(스냅샷 복원 후)
4. 매 실행의 `report.json` / `capture.pcap` / 소요시간을 팀에 공유 ← **B·D의 작업이 이 산출물에 물려 있으므로 최우선**
5. `views/dynamic_view.py` 실측 검증 + 커밋된 테스트 추가 (현재 동적 뷰 테스트 0개)

### D — 백소정 (네트워크 / 위험도)

1. **tcpdump 문제 해결** — 7주차 e2e를 막고 있는 유일한 블로커. `src/network_analyzer/capture.py` 소유자가 D이므로 주관, adb/에뮬레이터 쪽은 C 지원
   - 확인 순서: 에뮬레이터 root 여부 → `/system/bin/tcpdump` 존재 여부 → 쓰기 가능 경로 → pcap pull
   - 안 되면 대안: 에뮬레이터 `-tcpdump <file>` 실행 옵션으로 호스트 측 캡처. **이 대안을 Day 2까지 못 뚫으면 즉시 전환**하고 파이프라인을 막지 않는다
2. **점수 재조정** — 8주차의 핵심 산출물
   - `risk_scorer.NORMALIZATION_CAP`: 현재 100, 실측 raw 140 발생 → 상한을 올려 상위 구간이 뭉개지지 않게
   - `risk_aggregator`: `MODULE_WEIGHTS`, `DYNAMIC_CAP`, `NETWORK_CAP`, `LEVEL_THRESHOLDS`
   - **기준: 정상 2개는 low, 악성 2개는 high로 갈리고, 그 사이 간격이 충분히 벌어질 것.** 조정 근거(샘플별 실측 점수 표)를 반드시 남긴다 — 숫자를 맞추려고 임계값을 옮긴 것과 구분되어야 함
3. `views/network_view.py` 실측 검증 + 테스트 추가
4. 정적↔네트워크 대조 (B의 D-3): `strings.urls` / `strings.ip_addresses`와 실제 관측 도메인 대조. **여유 있으면 진행, 없으면 8주차 이후로 넘김**

## 3. 시간 단축 정량화 방법 (B 주관)

정직하게 측정하지 않으면 발표에서 가장 먼저 깨지는 숫자이므로 방법을 미리 고정한다.

### 왜 "3~6월에 몇 달 걸렸다"를 그대로 쓰면 안 되는가

- 그 기간은 **학습 시간이 대부분**이고 순수 분석 시간이 아님
- 비교 대상이 다름 — 사람은 앱 전체를 이해했고, 도구는 정해진 항목만 뽑음

### 대신 이렇게 측정한다 — "동일 산출 항목"에 대한 비교

대시보드가 내놓는 항목만 골라, 같은 항목을 손으로 뽑는 데 걸리는 시간을 잰다.

| 산출 항목 | 수동 방법 | 자동 |
|---|---|---|
| 요청 권한 목록 + 위험 권한 식별 | jadx로 Manifest 열람 | 정적 탭 |
| 서명 인증서 / 자가 서명 여부 | keytool | 정적 탭 |
| 난독화·리플렉션·동적 로딩 흔적 | jadx 코드 검색 | 정적 탭 |
| 외부 노출 컴포넌트 | Manifest exported 확인 | 정적 탭 |
| 런타임 민감 API 호출 | Frida 스크립트 작성 + 실행 | 동적 탭 |
| DNS 질의 / 접속 도메인 목록 | Wireshark 필터링 | 네트워크 탭 |
| 의심 도메인 판별 | 도메인 하나씩 조회 | 네트워크 탭 |

**측정 규칙**

1. 측정자는 **이미 그 작업에 숙련된 상태**여야 함 (학습 시간 제외). 3~6월 분석 경험자가 측정
2. 스톱워치 기준, 항목별로 따로 잰다. 도구 실행 대기 시간은 포함
3. 자동 쪽은 A의 `report["timing"]` 값 + 사람이 화면을 읽는 시간을 별도 표기
4. **샘플 1개당 1회씩, 악성 1개 + 정상 1개** 최소 2세트

**산출물**: 항목별 `수동 N분 vs 자동 N초` 표 + 총합 배수 1개

**한계 명시 (반드시 발표 자료에 포함)**

- 표본 n=2, 측정자 1인 → 통계적 유의성 주장 금지
- 자동화가 대체하는 것은 **"정해진 항목 추출"**이지 **"분석 판단"**이 아님
- 사람만 할 수 있는 것(왜 그 권한 조합이 위험한지 해석, 새로운 은닉 기법 발견)은 줄어들지 않음 — 이 점을 먼저 말하는 편이 숫자의 신뢰도를 높임

### 4-1. jsonschema 4.26.0 — 회귀 없음 (D의 7주차 5번 항목 종결)

- 4.26.0 설치 후 전체 테스트 재실행 → 통과
- D가 예상한 대로 `Draft7Validator` 단일 스키마 경로는 3.x ↔ 4.x 동작 동일
- 단, 이 확인 과정에서 별건인 8번이 드러남 (아래)

### 4-2. `risk_view` 더미 점수 — 8주차 e2e 전에 반드시 고쳐야 했던 것

**증상**: 세 모듈이 전부 실패해 `risk_score.total = None`인 리포트에서, 종합 위험도 탭에 **56px 빨간 "72 / 100 · 위험"** 이 뜸. "예시 데이터" 배너가 같이 뜨지만 화면에서는 숫자가 먼저 읽힘.

**왜 생겼나**: 7주차 시점에는 `aggregate_risk()`가 아직 배선 전이라 `total=None`이 "스코어링 미반영"을 뜻했고, 더미를 그리는 것이 계획상 맞았음(7주차 계획 D 항목의 "했다고 치고"). PR #8로 실제 계산이 `main.py`에 붙으면서 `total=None`의 의미가 **"세 모듈 전부 실패"** 로 바뀌었는데 뷰는 그대로 남음.

**왜 8주차에 치명적인가**: 8주차는 실샘플 e2e 주간이고, C의 7주차 기록대로 초기 실행은 대부분 실패로 끝남. 그 화면을 그대로 캡처하면 **분석에 실패한 앱을 "위험 72점"으로 발표**하게 됨.

**수정**: `total=None`이면 `common`에 이미 있던 `unknown` 상태(회색 · "판정 불가")를 그리고 점수·게이지·기여도 표를 전부 그리지 않음. 어느 모듈이 왜 죽었는지를 대신 표시. 더미는 `st.session_state["risk_view_demo"]`를 켤 때만 나오며, 그 자리는 `demo_risk.py`(D가 기기 없이 화면 작업하는 용도, B의 `demo_static.py`와 같은 방식).

- `aggregate_risk()`가 `total=None`/`level="unknown"`을 굳이 따로 두는 이유(실패를 0.0=안전으로 오해하지 않게)와 뷰를 일치시킨 것
- 재발 방지 테스트 7개 추가(`tests/test_risk_view_render.py`). 일부러 되돌려 확인한 결과 6개가 검출(B의 기존 정적 렌더링 테스트 1개 포함)
