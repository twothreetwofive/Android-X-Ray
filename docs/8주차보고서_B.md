## 1. 실행 환경 구축 — WSL + Windows 에뮬레이터

### 1-1. 구조

- 코드·파이썬·pytest = **WSL(Ubuntu 22.04)**
- 에뮬레이터 = **Windows** (WSL2에 `/dev/kvm` 없어 리눅스 쪽 기동 불가)
- 따라서 WSL의 파이썬이 Windows의 에뮬레이터를 조작해야 함

```
[WSL]  src/main.py ─ adb ─┐
       frida ─────────────┤ 127.0.0.1:5037
                          ↓  adb-bridge (TCP 중계)
[Windows] adb 서버 (172.25.144.1:5037) → 에뮬레이터
```

- `frida`는 `ADB_SERVER_SOCKET` 환경변수를 보지 않고 **항상 127.0.0.1:5037**에 붙음 → 환경변수만으로는 해결 불가, 중계가 필요한 이유

### 1-2. 설치 도구 (전부 `~/tools`, sudo 불필요)

| 도구 | 버전 | 비고 |
|---|---|---|
| JRE | 17 | apktool·jadx 구동 |
| apktool | 3.0.3 | |
| jadx | 1.5.6 | |
| adb (Linux) | **37.0.0** | Windows adb와 **반드시 동일 버전** |
| frida (python) | 17.16.2 | |
| frida-server | 17.16.2 (x86_64) | 기기 ABI에 맞춰야 함 |

### 1-3. 연결에서 겪은 문제 2종 (팀원도 반드시 겪을 것)

**(1) adb 버전 불일치**

- WSL 37.0.1 / Windows 37.0.0 조합에서, WSL 클라이언트가 **원격 서버를 죽이고** 자기 로컬 서버를 띄움
- 증상: Windows에서는 기기가 보이는데 WSL `adb devices`는 빈 목록. Windows 로그에 `adb server killed by remote request`
- 해결: WSL 쪽 platform-tools를 Windows와 같은 버전으로 맞춤

**(2) `adb kill-server` 자충수**

- 중계(adb-bridge)가 떠 있는 상태에서 이 명령을 치면 중계를 타고 넘어가 **Windows 쪽 adb 서버를 죽임**
- 증상: `Address already in use` + `Connection reset by peer` 동시 발생
- 해결: 손으로 치지 말고 `scripts/connect_emulator.sh` 하나만 쓸 것 (상태를 먼저 보고 필요한 것만 수행, 몇 번 실행해도 안전)

### 1-4. 팀 공용 AVD 실측 사양

```
ro.product.cpu.abilist = x86_64,x86,arm64-v8a,armeabi-v7a,armeabi
ro.build.version.sdk   = 30
adb root               = 성공
/system/bin/tcpdump    = 존재      ← 7주차에 C가 막혔던 지점, 복사만 하면 됨
```

- `arm64-v8a`가 목록에 있음 = **ARM 변환 내장** → 샘플 ABI 제약이 사실상 없음
- SDK가 두 벌 설치돼 있고(`C:\Android_AVD`, `%LOCALAPPDATA%\Android\Sdk`) 에뮬레이터는 **전자**에서 돎. adb 경로를 헷갈리면 기기가 안 보임

### 1-5. 추가한 스크립트

| 스크립트 | 역할 |
|---|---|
| `scripts/wsl_env.sh` | apktool/jadx/adb PATH 설정 (매 터미널 1회) |
| `scripts/connect_emulator.sh` | Windows adb 서버 + 중계 + 기기 확인을 한 번에 |

## 2. 대시보드·출력 개편 — 분석 상태 ≠ 보안 판정

계획수정 PDF 1~5항을 코드 수준에서 반영함.

### 2-1. 문제

- 모듈 상태 "✅ 정상"이 **"이 APK가 안전하다"**로 읽혔음. 실제 의미는 "정적 분석이 정상적으로 실행됨"
- 평문 후보 35건이 나온 취약 APK가 세 모듈 모두 "정상"으로 표시되던 것이 그 증거

### 2-2. 변경

| 항목 | 이전 | 이후 |
|---|---|---|
| 상태 라벨 | 정상 / 부분 실패 / 실패 / 타임아웃 | **분석 성공 / 부분 성공 / 분석 실패 / 시간 초과** |
| 판정 구간 | low / medium / high (0.34, 0.67) | **0–29 정상 / 30–59 주의 / 60–79 의심 / 80–100 고위험** |
| 최종 판정 | 없음 (탭 안 점수만) | 탭 **위**에 판정 카드 신설 (`views/verdict_header.py`) |
| 위험 지표 | 점수에 섞여 있음 | 별도 층으로 분리, 모듈 탭 상단에도 표시 |
| 고지 문구 | 없음 | 화면·CLI 하단 고정 |

### 2-3. "악성" 표시 잠금 (PDF 5항)

- 점수만으로 "악성"이라 쓰지 않음. **종합 80점 이상 그리고 강한 지표 3개 이상**을 둘 다 충족할 때만 승격
- 화면에 **승격하지 않은 이유**를 그대로 노출함 (예: "현재 44점 / 강한 지표 1개")
- **강한 지표에서 제외한 것**: 평문 후보, 의심 도메인 1~2건
  - 근거: 평문 처리는 취약 실습 앱의 대표 특징이라 악성 판별력이 낮음. 화이트리스트(`whitelist_checker.py`)와 IP 검사(`ip_checker.py`)는 스스로 불완전하다고 명시하고 있어 오탐이 섞임

### 2-4. 점수 상수 재조정

- **개수가 아니라 종류의 다양성을 봄.** 지표 종류마다 반영 개수 상한을 둠
- 근거: 이전 상수(평문 8점/건, CAP 50)로는 평문 7건이면 동적 점수가 포화됨 → 취약 앱과 악성 앱이 점수에서 구분되지 않음
- 검증: PDF 2항이 든 사례(평문 35 + 의심 도메인 1 + 의심 IP 3)를 넣으면 **이전 92점 "악성" → 현재 64점 "의심"**

### 3-2. 정상 앱을 위험하게 보이게 하던 오탐

에뮬레이터 내장 시계 앱이 **87점 "고위험"**으로 나온 것이 계기임.

| 오탐 | 조치 |
|---|---|
| 의심 API를 **건수×3**으로 계산 (번들 라이브러리 포함, 42점) | `code_scanner`가 이미 매긴 risk별 가중치 + 같은 API는 한 종류로 + 상한 |
| `자체 서명` 10점 — 안드로이드 앱은 **거의 전부** 자체 서명이라 변별력 없음 | 2점 |
| exported 컴포넌트 무제한 (11개 = 22점) | 상한 12점 |
| IP 정규식이 `8.4.91.697`을 IP로 인식 | 옥텟 범위 검증 |
| 평문 후보 124건이 전부 프레임워크 호출 (`java.util.Formatter` 120건 등, **앱 코드 0건**) | hooks.js가 주는 `caller_class`로 프레임워크 호출 제외. 원본 events는 보존, 제외 건수 기록 |
| androguard DEBUG 로그 수천 줄이 결과를 덮음 | 기본 억제, `--verbose`로 복원 |

**결과: 시계 앱 87점 "고위험" → 28점 "정상"**

### 3-3. 대시보드 전용 버그

- 증상: UI로 APK를 올리면 정적만 성공하고 동적·네트워크가 실패. 같은 APK를 CLI로 돌리면 세 모듈 다 성공
- 원인: **업로드는 파일을 임시 폴더에 저장할 뿐 에뮬레이터에 설치하지 않음.** 동적 분석은 설치된 패키지를 frida로 띄우는 구조
- CLI에서는 `prepare_emulator.sh`가 설치를 대신 해줘서 안 드러났을 뿐이고, **새 샘플은 어떤 것이든 UI만으로는 실패**했음
- 조치: `preflight.py` 추가 — 분석 직전에 adb PATH / 기기 연결 / **앱 설치(없으면 자동 설치)** / frida-server / tcpdump를 점검하고, 못 고치는 것은 "무엇을 실행하면 되는지"까지 화면에 안내

### 4-3. 드로퍼 분석 — 네트워크가 비어 있던 진짜 이유

네트워크 지표가 0이라 모듈 버그를 의심했으나, **대조 실험**(기기에서 `ping` 발생시키며 캡처)에서 DNS·ICMP가 정상 캡처됨 → tcpdump는 정상.

frida 없이 45초 실행해도 외부 트래픽 0건. 앱은 정상 실행되어 다음 경로로 진입:

```
LaunchRouterActivity → com.shell.template.feature.upgrade.UpgradeActivity
화면 = 전체 WebView (id/webViewContainer)
```

**통신하지 않는 이유는 페이로드를 이미 품고 있기 때문임:**

```
assets/f80at32d.zip
  크기      8,331,772 bytes = APK 전체의 94.9%
  매직바이트 "SVLT"  (알려진 포맷 아님)
  엔트로피   7.906 / 8.0  → 암호화된 데이터
```

- 구조: 암호화된 2차 APK를 내장 → WebView가 **로컬** 업그레이드 페이지(`appassets.shelltemplate.internal`)를 띄움 → JS 브리지(`window.ShellApp.onState`)로 설치 유도 → `REQUEST_INSTALL_PACKAGES`로 설치
- 스말리에 중국어 문자열 잔존(`初始化升级页面失败`)
- 앱 이름에 **제로폭 문자 13개** 삽입 — 이름 기반 탐지 회피
- 표준 안드로이드 권한은 `REQUEST_INSTALL_PACKAGES` **하나뿐**이고 나머지 84개는 앱 자체 정의 권한

**우리 정적 분석이 이걸 놓친 이유**: jadx 소스만 훑고 apktool의 `assets/`를 보지 않았음. 코드 기준 분석으로는 **원리상 볼 수 없는 위치**에 실체가 있었음.

→ `code_scanner._detect_packed_assets()` 추가. **큰 파일 + 높은 엔트로피 + 알려진 매직바이트 아님**을 모두 만족하는 덩어리를 탐지하고 강한 지표로 등록함(정상 앱의 폰트·이미지·압축 자산은 매직바이트로 걸러짐).

## 5. 미해결 — 팀 논의 필요

### 5-1. 점수만으로는 정상/악성이 분리되지 않음

- 캘린더(46)와 드로퍼(44)가 **역전**돼 있음
- 원인 두 가지 모두 실제 사실임
  - 캘린더의 정적 점수가 진짜로 높음 (권한 25개, exported 28개, `PathClassLoader`·`OkHttpClient` 실제 사용)
  - 휴면형 드로퍼는 사용자가 WebView를 누르기 전까지 아무 동작도 하지 않아 동적 관측이 진짜로 적음
- **정적 점수만 보면 37 / 56 / 69로 분리됨**
- 표본 3개로 상수를 더 맞추면 과적합이므로 중단함. 팀원 결과가 합쳐져 8종이 되면 그때 재검토할 것

### 5-2. 적용한 정책 — "관측 없음"은 "위험 없음"이 아님

- 정상 실행됐지만 아무것도 관측하지 못한 모듈은 **실패 모듈과 동일하게 제외 + 가중치 재정규화**
- 선택 근거: 새 규칙이 아니라 이 저장소가 이미 세 곳에서 지키던 원칙을 빠진 한 곳에 적용한 것
  - `static_data.py`: 점수가 없을 때 0으로 채우지 않음
  - `risk_view._render_unknown()`: 빈 게이지·0점 대신 "판정 불가"
  - `aggregate_risk()`: 실패 모듈은 0점이 아니라 제외
- 화면에서는 "분석 실패"와 **"관측된 데이터 없음(분석은 성공)"**을 구분 표시함
- 대안이었던 "강한 지표 하한"은 지표가 판정을 직접 밀어올리는 새 휴리스틱이라 PDF의 "확정하지 않는다" 기조와 결이 다름. "가중치 조정"은 표본 3개 과적합

### 5-3. 그 외 이월 과제

- `NORMALIZATION_CAP` 상한: 뱅킹 트로이목마 구성은 raw 137로 100에서 잘림
- 캡처에 frida 자체 트래픽(포트 27042)이 섞임 — tcpdump 필터로 제외 검토
- `login_flow` / `permission_request` 시나리오 좌표 미확정
  - 이번 드로퍼처럼 **사용자 상호작용을 기다리는** 샘플은 `LAUNCH_ONLY`로는 관측이 안 됨. WebView 버튼을 누르는 시나리오가 필요함
- outer timeout 트립 시 adb/frida 좀비 프로세스 정리 (6주차부터 이월)
- hooks.js에 `WebView.loadUrl` 후킹 추가 검토 — 이번 샘플처럼 WebView로 동작하는 유형에 유효

## 6. 팀원 안내

### 6-1. 환경 구축

- `docs/8주차_로컬테스트_가이드.md` 참고 (설치부터 대시보드까지 단계별 명령)
- 순서: `source scripts/wsl_env.sh` → `bash scripts/connect_emulator.sh` → `bash scripts/prepare_emulator.sh`

### 6-2. 샘플 취급 규칙

- **저장소에 절대 커밋 금지.** `.gitignore`에 `*.apk` `*.apk_` `*.dex` `*.zip` `samples/` 등록함
  - MalwareBazaar 배포본은 AES 암호화 zip이라 기존 `*.apk` 규칙으로 안 걸렸음. 실제로 저장소 루트에 받아둔 적 있어 규칙을 넓힘
- 샘플은 `~/samples/`에만 둘 것
- MalwareBazaar zip은 **AES 암호화**라 Windows 기본 압축 해제로는 안 풀림. 7-Zip 또는 `pyzipper` 필요. 비밀번호 `infected`
- **실행 전 스냅샷 저장 필수**: `bash scripts/snapshot.sh save before_run`
  - 드로퍼는 2차 페이로드를 **별도 패키지로** 설치하므로 `adb uninstall`만으로는 정리되지 않음
- 받은 APK는 먼저 `python3 scripts/check_apk_compat.py ~/samples/*.apk`로 거를 것

### 6-3. 실행

```bash
# 정적만 (에뮬레이터 불필요)
python3 src/main.py ~/samples/<파일>.apk --output output/report_<이름>.json

# 전체 파이프라인
bash scripts/prepare_emulator.sh ~/samples/<파일>.apk
python3 src/main.py ~/samples/<파일>.apk --output output/report_<이름>.json --observe-sec 15

# 대시보드 (업로드 시 에뮬레이터 설치까지 자동)
streamlit run app.py
```

### 6-4. 검토 요청

- 5-1(점수 분리 실패)에 대한 의견 — 각자 샘플 결과를 모아 8종으로 재검토할 것을 제안함
- 5-3의 시나리오 좌표 작업은 D 역할이나, 대상 앱이 정해져야 진행 가능함
