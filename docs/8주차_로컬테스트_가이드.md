# 8주차 로컬 테스트 가이드 (WSL + Windows 에뮬레이터)

**작성 기준**: 2026-08-13, 브랜치 `feature/8w-b-cleanup`
**대상**: 8주차 계획수정 PDF의 "실제 로컬에서 환경 구축 및 실행 → apk 넣어서 오류 발생 확인 및 오류 해결"
**샘플 취급**: 분석용 APK는 **저장소에 절대 커밋하지 않음**. `.gitignore`에 `*.apk`/`*.zip`/`*.dex`/`samples/` 등록됨. 샘플은 `~/samples/`에만 둘 것

## 0. 이 PC의 구조 — 먼저 이해할 것

- 코드·파이썬·pytest = **WSL(Ubuntu 22.04)**
- 에뮬레이터 = **Windows** 에서만 실행 가능 (WSL2에 `/dev/kvm` 없음)
- 따라서 **WSL의 파이썬이 Windows의 에뮬레이터를 조작**해야 하고, 그 통로가 `adb-bridge`

```
[WSL]  src/main.py ─ adb 클라이언트 ─┐
                     frida ──────────┤ 127.0.0.1:5037
                                     ↓
                        adb-bridge (TCP 중계)
                                     ↓
[Windows] adb 서버 (172.25.144.1:5037) → 에뮬레이터
```

- `frida`는 `ADB_SERVER_SOCKET` 환경변수를 보지 않고 **항상 127.0.0.1:5037**에 붙음 → 환경변수만으로는 해결 안 되고 중계가 필요한 이유

## 2. 팀 공용 AVD 사양 (2026-08-13 실측)

**주의: SDK가 두 벌 깔려 있음.** 에뮬레이터는 `C:\Android_AVD` 쪽에서 돌고,
`%LOCALAPPDATA%\Android\Sdk`는 쓰이지 않음. adb 경로를 헷갈리면 기기가 안 보임.

실행 중인 에뮬레이터에서 직접 읽은 값:

```
ro.product.cpu.abilist = x86_64,x86,arm64-v8a,armeabi-v7a,armeabi
ro.build.version.sdk   = 30          (Android 11)
ro.product.model       = sdk_gphone_x86_64
adb root               = 성공        (tcpdump 캡처 가능)
/system/bin/tcpdump    = 존재        (7주차 C가 막혔던 지점 — 복사만 하면 됨)
```

**핵심: `arm64-v8a` / `armeabi-v7a`가 목록에 있음 = ARM 변환 내장.**
안드로이드 악성코드 상당수가 ARM 전용인데, 이 AVD는 그것도 설치·실행됨.
즉 **샘플 선택에 ABI 제약이 사실상 없음.** minSdk ≤ 30만 확인하면 됨.

받은 APK 확인(에뮬레이터가 붙어 있으면 실제 사양을 자동 감지함):

```bash
python3 scripts/check_apk_compat.py ~/samples/*.apk
```

## 3. 샘플 APK 확보

### 3-1. 악성 샘플 — MalwareBazaar

1. https://auth.abuse.ch/ 에서 **무료 계정 생성 → Auth-Key 발급** (API·다운로드 모두 인증 필수. 인증키 없이 호출하면 `{"error": "Unauthorized"}`)
2. https://bazaar.abuse.ch/browse/ 에서 검색
   - **`file_type: apk`로 반드시 필터.** `elf` 태그는 Linux/IoT 계열(Mirai 등)이라 안드로이드가 아님
   - 태그로 계열 검색도 가능: `SpyNote`, `Cerberus`, `Hydra`, `Ermac`, `FluBot`, `Joker`
3. 다운로드 zip 비밀번호는 공통으로 **`infected`**

API로 받는 경우:

```bash
KEY=발급받은_키
# 태그로 목록 조회
curl -s -X POST https://mb-api.abuse.ch/api/v1/ \
     -H "Auth-Key: $KEY" \
     -d "query=get_taginfo" -d "tag=apk" -d "limit=50" | python3 -m json.tool | less

# sha256으로 다운로드
curl -s -X POST https://mb-api.abuse.ch/api/v1/ \
     -H "Auth-Key: $KEY" \
     -d "query=get_file" -d "sha256_hash=<해시>" -o ~/samples/sample.zip
cd ~/samples && 7z x -pinfected sample.zip     # 또는 unzip -P infected
```

**어떤 계열을 고를지** — ABI 제약이 없으므로(2장) 동적·네트워크에서 볼거리가 많은 순:

| 우선순위 | 계열 | 이유 |
|---|---|---|
| 1순위 | **SpyNote / AhMyth 계열 RAT** | C2로 주기적 통신 → 네트워크 모듈에 실제로 잡힘. SMS·연락처·녹음 권한이 많아 정적 권한 표도 채워짐 |
| 2순위 | **Cerberus / Hydra / Ermac** (뱅킹) | Anubis와 같은 계열이라 3~6월 분석 경험과 직접 비교 가능. 접근성+오버레이+SMS 조합이라 "고위험 권한 조합" 강한 지표가 실제로 뜨는지 검증됨 |
| 3순위 | **Joker / FluBot 드로퍼** | 드로퍼는 본체가 작아 설치는 잘 되지만, 실행 직후 페이로드를 받아오지 못하면 관측되는 게 적을 수 있음 |

- 실무적으로는 **후보 5~10개를 받아 `check_apk_compat.py`로 거른 뒤** 통과한 것 중 주목 권한이 많은 것을 고르는 편이 빠름
- 팀 내 중복 금지: 백소정·김은아가 이미 가져간 파일과 겹치지 않게 확인할 것. `anubis.apk` / `syssecapp.apk`는 PDF에서 제외 대상

### 3-2. 정상 앱 (대조군)

**AVD에 이미 깔려 있는 앱을 그대로 쓰면 됨.** 별도로 받을 필요 없고, 오히려 이쪽이 확실함
— 이미 그 기기에서 도는 앱이라 설치 실패가 없고, 구글 서명 정품이라 "정상 앱" 대조군으로서 근거도 분명함.

```bash
# 1) 설치된 앱 목록에서 고르기
adb shell pm list packages | grep -iE "calculator|deskclock|calendar|chrome|contacts"

# 2) 고른 앱의 APK 경로 확인
adb shell pm path com.google.android.deskclock
#   package:/product/app/PrebuiltDeskClockGoogle/PrebuiltDeskClockGoogle.apk

# 3) 뽑아오기 (실측으로 확인된 경로)
adb pull /product/app/PrebuiltDeskClockGoogle/PrebuiltDeskClockGoogle.apk ~/samples/deskclock.apk
adb pull /product/app/CalendarGooglePrebuilt/CalendarGooglePrebuilt.apk   ~/samples/calendar.apk
```

성격이 다른 2개를 고르면 점수 대비가 잘 드러남:

| 종류 | 예 | 기대 결과 |
|---|---|---|
| 최소 권한 | `com.google.android.deskclock`(시계) — 권한 11개 | 위험도 최저(정상 구간). 점수 하한 검증 |
| 네트워크 사용 | `com.google.android.calendar` — 권한 25개 | 정상 도메인이 화이트리스트를 통과하는지 = 오탐 검증 |

> `com.android.chrome`도 있지만 APK가 커서 디컴파일에 오래 걸림. 시간 없으면 위 둘로 충분함

- 밖에서 받고 싶으면 **F-Droid**(https://f-droid.org)를 권함. 오픈소스라 로그인 없이 APK 직접 다운로드 가능
- APKPure/APKMirror도 되지만 받은 뒤 `check_apk_compat.py`로 minSdk를 확인할 것

### 3-3. 취급 규칙 (8주차 계획 1항)

- 저장소에 커밋 금지. `~/samples/` 밖으로 옮기지 말 것
- **샘플 실행 전 스냅샷 저장, 실행 후 복원.** 드로퍼는 실행되면 2차 페이로드를
  **별도 패키지로** 설치하므로, 원래 앱을 `adb uninstall` 해도 기기가 깨끗해지지 않음.
  통째로 되돌리는 방법은 스냅샷뿐임

```bash
bash scripts/snapshot.sh list              # 목록
bash scripts/snapshot.sh save before_run   # 저장 (40초쯤 걸림)
bash scripts/snapshot.sh load before_run   # 복원
```

> `adb emu` 명령은 에뮬레이터 콘솔 포트(5554)에 직접 붙는데 그 포트는 Windows
> 로컬에만 열려 있어서 WSL에서 그냥 치면 `Connection refused`가 남. 위 스크립트가
> Windows adb.exe로 넘겨서 처리함.
>
> **복원 후에는 `bash scripts/prepare_emulator.sh`를 다시 실행할 것** — 스냅샷 시점에
> frida-server가 떠 있지 않았다면 꺼진 상태로 돌아옴.

## 5. 2단계 — 에뮬레이터 연결

### 5-1. 에뮬레이터 켜기

Android Studio의 Device Manager에서 실행하거나, PowerShell에서:

```powershell
cd C:\Android_AVD\emulator
.\emulator.exe -avd <AVD이름> -writable-system
```

> WSL에서 `emulator.exe`를 실행하면 `could not load PC BIOS`로 실패함. 반드시 Windows에서 띄울 것.

### 5-2. WSL에서 연결 — 명령 하나

```bash
cd ~/ecops_2325
source scripts/wsl_env.sh
bash scripts/connect_emulator.sh
```

성공 시:

```
== 1. Windows adb 서버 (172.25.144.1:5037) ==
  [OK]   재기동 완료
== 2. WSL 중계 (127.0.0.1:5037) ==
  [OK]   중계 시작
== 3. 기기 확인 ==
  emulator-5554	device
  [OK]   연결됨: emulator-5554   ABI=x86_64 API=30
```

이 스크립트가 하는 일: Windows adb 서버가 WSL에서 닿는지 확인 → 안 닿으면 `-a`(모든 인터페이스)로 재기동 → 중계(adb-bridge) 상태 확인 후 필요할 때만 시작 → 기기 확인. **몇 번을 실행해도 안전함**(idempotent).

### 5-3. 손으로 하지 말 것 — 두 가지 함정

1. **`adb kill-server`를 직접 치지 말 것.** 중계가 이미 떠 있으면 이 명령이 중계를 타고 넘어가 **Windows 쪽 adb 서버를 죽임**. 그러면 `Address already in use`와 `Connection reset by peer`가 동시에 나옴
2. **WSL adb와 Windows adb는 버전이 같아야 함.** 다르면 WSL 클라이언트가 "서버 버전이 다르다"며 원격 서버를 죽이고 자기 로컬 서버를 띄움 → 기기가 안 보임. Windows 로그에 `adb server killed by remote request`로 남음
   - 실제로 WSL 37.0.1 / Windows 37.0.0 조합에서 발생함. WSL 쪽을 37.0.0으로 맞춰 해결
   - `connect_emulator.sh`가 시작할 때 버전을 비교해서 다르면 멈추고 알려줌

## 6. 3단계 — 에뮬레이터 사전 준비 (tcpdump / frida-server)

**이 단계를 건너뛰면 7주차에 C가 멈춘 지점(tcpdump 에러)에서 똑같이 멈춤.**
`capture.py`가 `/data/local/tmp/tcpdump`를 하드코딩해 확인하고, `scenario_capture.py`가 push 없이 호출하기 때문에 없으면 동적·네트워크가 **둘 다** 실패함.

```bash
cd ~/ecops_2325
bash scripts/prepare_emulator.sh ~/samples/<샘플>.apk
```

하는 일: 기기 확인 → `adb root` → tcpdump 준비 → ABI에 맞는 frida-server push·실행 → APK 설치(`-g`로 권한 부여).

수동으로 하려면:

```bash
adb root
adb shell "cp /system/bin/tcpdump /data/local/tmp/tcpdump && chmod 755 /data/local/tmp/tcpdump"
adb push ~/tools/frida-server-17.16.2-android-x86_64 /data/local/tmp/frida-server
adb shell chmod 755 /data/local/tmp/frida-server
adb shell "nohup /data/local/tmp/frida-server >/dev/null 2>&1 &"
frida-ps -U | head
adb install -r -g ~/samples/<샘플>.apk
```

**tcpdump가 이미지에 없을 때 대안**: 에뮬레이터를 `-tcpdump` 옵션으로 띄우면 호스트에서 직접 pcap을 뜰 수 있음(파이프라인 자동화는 안 되지만 pcap 확보는 됨).

```powershell
.\emulator.exe -avd <AVD이름> -writable-system -tcpdump C:\temp\capture.pcap
```

## 9. 화면 구조 (8주차 개편 — 계획수정 PDF 반영)

**분석 상태(Status) ≠ 보안 판정(Verdict)** 를 코드 수준에서 분리함.

```
              APK 보안 분석 결과
            🟠 의심 (SUSPICIOUS)
           종합 위험도  64 / 100
─────────────────────────────────────
분석 상태  (앱의 안전 여부가 아니라 실행 성공 여부)
  정적 분석  ✅ 분석 성공   동적 분석  ✅ 분석 성공   네트워크  ✅ 분석 성공
─────────────────────────────────────
[탭] 정적 / 동적 / 네트워크 / 종합 위험도
   각 탭 상단: 분석 상태 + 위험 지표 두 줄
   종합 탭: 위험 지표 표 → 모듈별 위험도 → 게이지 → 기여도 → 판정 근거 → 주의 문구
```

- 상태 라벨: `정상/실패` → **`분석 성공/부분 성공/분석 실패/시간 초과`**
- 판정 구간: **0–29 정상 / 30–59 주의 / 60–79 의심 / 80–100 고위험**
- **"악성"은 점수만으로 주지 않음**: 종합 80점 이상 **그리고** 강한 지표 3개 이상을 둘 다 충족할 때만. 화면에 "악성으로 표시하지 않은 이유"를 그대로 노출함
- 모든 화면·CLI 하단에 고지 문구 고정

## 10. 트러블슈팅

| 증상 | 원인 | 조치 |
|---|---|---|
| `'apktool' 실행 파일을 찾을 수 없음` | PATH 미설정 | `source scripts/wsl_env.sh` |
| `adb devices`가 비어 있음 | Windows adb 서버 미기동 / 중계 미실행 | 5-2, 5-3 확인. `pgrep -f adb-bridge` |
| `adb-bridge` 바인드 실패 | WSL에 로컬 adb 서버 존재 | `adb kill-server` 후 재실행 |
| `Frida 연결 실패: device not found` | frida-server 미실행 | `adb shell pidof frida-server` 확인 |
| `unable to connect to 127.0.0.1:27042` | frida 버전 불일치 | 파이썬 frida와 frida-server 둘 다 17.16.2인지 확인 |
| `TcpdumpCaptureError: 기기에 tcpdump가 없고...` | `/data/local/tmp/tcpdump` 없음 | 6단계 수행 |
| `tcpdump가 기기에서 시작되지 않았습니다` | root 아님 | `adb root` 후 `adb shell whoami` |
| `INSTALL_FAILED_NO_MATCHING_ABIS` | APK ABI ≠ 기기 ABI | 이 AVD는 ARM 변환이 있어 거의 발생 안 함. 나면 `check_apk_compat.py`로 확인 |
| `Address already in use` + `Connection reset by peer` | 손으로 `adb kill-server`를 침 | `bash scripts/connect_emulator.sh` 하나만 쓸 것 (5-3 참고) |
| WSL `adb devices`는 비었는데 Windows는 기기가 보임 | adb 버전 불일치 | WSL/Windows adb 버전을 맞출 것 (5-3) |
| `could not load PC BIOS` | WSL에서 emulator.exe 실행 | Windows에서 실행. 잔여 `qemu-system-x86_64-headless`는 작업 관리자에서 종료 |
| `Another emulator instance is running` | 이전 인스턴스 잔존 | 작업 관리자에서 qemu 종료 후 재시도 |

## 11. 남은 과제

- **점수 상수 실샘플 검증**: 구간·가중치·상한을 조정해 "취약 APK = 의심(60~79)", "정상 앱 = 정상(0~29)"이 되도록 맞췄으나, 근거가 합성 케이스임. 실제 정상 앱 2개 + 악성 2개로 돌려 재조정 필요 (`tests/test_risk_aggregator.py`의 케이스를 실측값으로 교체)
- `login_flow` / `permission_request` 시나리오 좌표 — 실제 대상 앱 확정 후 채워야 함
- outer timeout 트립 시 adb/frida 좀비 프로세스 정리 (6주차부터 이월)
